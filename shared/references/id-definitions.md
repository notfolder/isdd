# isdd ID定義（要件ID・設計ID）

isdd で使う ID 体系の定義。ID の書式と採番の規則はこのファイルを正とする。

---

## 要件ID（RQ-*）体系

### フォーマット

```
RQ-[カテゴリ]-[内容略称]
```

- 内容略称：英語 ALL CAPS ケバブケース（例: `CREATE-ORDER`）
- 連番なし、意味を表すスラッグのみ

### カテゴリ一覧

| カテゴリ | プレフィックス | 対象 |
|---|---|---|
| 業務 | `RQ-BZ` | 対象業務（業務一覧の業務単位） |
| 業務課題 | `RQ-BK` | 業務の問題（あるべき姿と現状のギャップ）を解決するために取り組むアクション・テーマ |
| 経営効果 | `RQ-EF` | 業務課題の解決で見込める経営効果 |
| 機能 | `RQ-FT` | 業務機能・ユースケース・業務ルール |
| 画面・出力 | `RQ-UI` | 利用者向けの入出力（画面、帳票・出力ファイル、Web API） |
| 外部連携 | `RQ-EX` | 外部システム連携 |
| テストシナリオ | `RQ-TS` | テスト要件 |
| 非機能 | `RQ-NF` | 利用者とアクセス経路・性能・可用性・移行性・セキュリティ |
| データ | `RQ-DT` | データ定義・保持ポリシー |
| 運用 | `RQ-OP` | 運用・バックアップ・監視 |

### 内容略称の命名規則（カテゴリ別）

| カテゴリ | 命名パターン | 例 |
|---|---|---|
| `RQ-BZ` | 業務名先頭（業務領域を端的に表す名詞） | `ORDER-MANAGEMENT`、`INVENTORY-CONTROL`、`CUSTOMER-SUPPORT` |
| `RQ-BK` | 取り組みを表す名詞先頭（問題そのものではなく、何に取り組むか） | `ORDER-ENTRY-AUTO-CHECK`、`MASTER-SYNC-AUTOMATION` |
| `RQ-EF` | 効果の種類と対象を表す名詞先頭 | `HARD-SAVING-OVERTIME`、`SOFT-SAVING-ORDER-ENTRY` |
| `RQ-FT`、`RQ-EX`、`RQ-TS` | 動詞先頭 | `CREATE-ORDER`、`SYNC-CUSTOMER-MASTER`、`VERIFY-ORDER-CANCEL` |
| `RQ-UI` | 画面・帳票・API の名前先頭 | `ORDER-CREATE-SCREEN`、`ORDER-CSV-EXPORT`、`ORDER-API` |
| `RQ-NF`、`RQ-DT`、`RQ-OP` | 名詞先頭 | `RESPONSE-TIME-2S`、`CUSTOMER-DATA-RETENTION`、`BACKUP-DAILY-POLICY` |

### 業務課題ID（RQ-BK）運用ルール

isdd では、すべての要件が業務課題から導かれていることを ID でたどれるようにする。業務課題に結びつかない要件は、作る理由を説明できないため残さない。

- 問題は業務のあるべき姿と現状のギャップ、課題（業務課題）は問題を解決するために取り組むアクションやテーマを指す。問題には ID を付けず、課題に `RQ-BK` を付ける
- 業務課題は `RQ-BK-[内容略称]` で採番する。機能要件より先に採番する
- `RQ-BK` と `RQ-BZ` 以外の要件（`RQ-EF`、`RQ-FT`、`RQ-UI`、`RQ-EX`、`RQ-TS`、`RQ-NF`、`RQ-DT`、`RQ-OP`）には、対応する `RQ-BK` を 1 つ以上、同じ表の「対応業務課題ID」の列に書く（チェッカーは同じ行に現れることで対応を判定する。ただし第 7 章の「検証する要件ID」列の ID は対応に数えない）
- `RQ-FT`・`RQ-UI`・`RQ-EX` は、第 7 章のシナリオ（`RQ-TS`）の「検証する要件ID」に 1 本以上現れる（チェッカーは現れない要件をエラーにする）
- `RQ-BK` に結びつかない要件が見つかったら、削除するか、業務課題を追加してから定義し直す

## 設計ID（DS-*）体系

### フォーマット

```
DS-[DSカテゴリ]-[DS内容略称]
```

- DS 内容略称は、設計要素そのもの（ファイル・クラス・関数・画面・テーブルなど）を表す英語 ALL CAPS ケバブケースにする（例: `DS-CL-ORDER-SERVICE`）。要件の略称は付けない。
- 要件 ID との対応は、設計書の「要件と設計の対応表」の章（design-chapters.md 第 11 章）だけに書く。ID に要件を埋めると、要件を差し替えたときに中身の変わらない設計要素まで ID を変えることになり、1 つの要素が複数の要件を受けるときに表せないため。
- isdd v2.0 までの、末尾に要件の略称を付けた長い設計 ID（例: `DS-CL-ORDER-SERVICE-FT-CREATE-ORDER`）もそのまま有効。書き換えなくてよい。新しく採番する ID だけを短い形にする。

### DSカテゴリ一覧（9種）

| カテゴリ | プレフィックス | 対象 |
|---|---|---|
| モジュール | `DS-MD` | ソースファイル（モジュール）単位。テストファイルを除くすべてのソースファイルに 1 つずつ付ける |
| インターフェース | `DS-IF` | 画面・コマンド・Web API・帳票・外部連携のインターフェース |
| クラス | `DS-CL` | クラス設計 |
| 関数 | `DS-FN` | 関数・メソッド設計 |
| データモデル | `DS-SC` | スキーマ・データモデル（DB を使わない場合のファイル形式・データ構造も含む） |
| バッチ | `DS-BT` | バッチ・ジョブ設計 |
| イベント | `DS-EV` | イベント・メッセージ設計 |
| テスト | `DS-TS` | E2E シナリオと、非機能要件を確かめるテスト |
| 運用 | `DS-OP` | 起動・初期化・設定・バックアップ・ログ・監視・障害対応 |

### 要件カテゴリと設計 ID の対応先

`RQ-BK`・`RQ-BZ`・`RQ-EF` 以外の要件は、すべて 1 つ以上の設計 ID で受ける（`rq_ds_link_checker.py` が確かめる）。どの種類の設計 ID で受けるかは次のとおり。

| 要件カテゴリ | 受ける設計 ID | 書く章（詳細設計書） |
|---|---|---|
| `RQ-FT`（機能・業務ルール） | `DS-FN`・`DS-CL`（バッチは `DS-BT`、イベントは `DS-EV`）と、それを置くファイルの `DS-MD` | 第 4・5・7 章 |
| `RQ-UI`（画面・帳票・Web API） | `DS-IF` | 第 4 章 4-1 |
| `RQ-EX`（外部連携） | `DS-IF`（連携のインターフェース）と、連携ライブラリの `DS-MD` | 第 4 章 4-1 |
| `RQ-DT`（データ・状態遷移） | `DS-SC`（状態遷移は遷移を行う `DS-FN` も） | 第 3 章 |
| `RQ-NF`（非機能） | 実現する設計要素（認証・認可なら `DS-CL`・`DS-FN`、性能なら `DS-SC` など）。実現する要素が無い場合は、確かめるテストの `DS-TS` | 第 3〜6 章、第 8 章 8-1 |
| `RQ-OP`（運用） | `DS-OP` | 第 9・10 章 |
| `RQ-TS`（テストシナリオ） | `DS-TS` | 第 8 章 8-2 |

ユーザーの承認を得て設計から外した要件は、設計書の「11-1. 除外要件」に書けば対応を求められない。

### ID例

| 要件ID（対応表の章に書く） | 設計ID | 説明 |
|---|---|---|
| `RQ-FT-CREATE-ORDER` | `DS-FN-CREATE-ORDER` | 注文作成機能の関数 |
| `RQ-FT-CREATE-ORDER`, `RQ-FT-CANCEL-ORDER` | `DS-CL-ORDER-SERVICE` | 注文の作成と取消を担うサービスクラス（1 つの要素が複数の要件を受ける） |
| `RQ-EX-SYNC-CUSTOMER-MASTER` | `DS-IF-SYNC-CUSTOMER-MASTER` | 顧客マスタ同期 API インターフェース |
| `RQ-TS-VERIFY-ORDER-CANCEL` | `DS-TS-ORDER-CANCEL-E2E` | 注文取消の E2E シナリオ |
| `RQ-OP-BACKUP-DAILY-POLICY` | `DS-OP-DAILY-BACKUP` | 日次バックアップの運用設計 |

## コードとの対応（対応表）

- ソースコードには要件 ID も設計 ID も書かない。コメントは通常のドキュメントコメント（処理の説明、引数、戻り値）だけにする。
- 設計 ID とコードの対応は `docs/trace_map.md`（対応表）で管理する。書式と粒度は対応表のルール（trace-map-rules.md）に従う。E2E シナリオ（`DS-TS-*`）はテスト関数に結ぶ。
- 要件 ID とコードの対応は、対応表の設計 ID から、設計書の「要件と設計の対応表」の章を引いて辿る。対応表に要件 ID は書かない。
- 対応表の整合は `trace_map_checker.py` で検証する。

## 廃止した ID

### モック方式の要件 ID `RQ-EX-USE-*`（isdd v2.1 で廃止）

isdd v2.0 まではモック方式を要件 ID（`RQ-EX-USE-*`）で表していた。モック方式はテストの設計判断なので、v2.1 からは設計書の 8-4 に書き、モックを `DS-TS-*` で設計する（design-chapters.md）。既存の要件定義書に `RQ-EX-USE-*` が残っていても有効なまま扱ってよい。

## ID採番ガイドライン

### 新しい RQ-* を採番するとき

1. カテゴリ一覧から選ぶ（「どのカテゴリか判断できない」場合はユーザーに確認する）
2. 内容略称をカテゴリ別命名規則に従って決める
3. 既存 ID と衝突しないか `docs/requirements.md` を確認する

### RQ-BZ を採番するとき

1. 業務名を短く・業務領域を端的に表す名詞で表現する
2. `RQ-BZ-[業務名略称]` で採番し、要件定義書の対象業務一覧へ登録する
3. 関連する業務課題（`RQ-BK-*`）と紐づける
4. 既存 ID と衝突しないか `docs/requirements.md` を確認する

### RQ-BK を採番するとき

1. 先に業務の問題（あるべき姿、現状、そのギャップ）を確定する
2. 問題を解決するために取り組むアクションやテーマを、業務課題として決める。「解決する問題」と「解決後の状態（KPI の目標値）」を書く
3. 取り組みを表す名詞先頭の内容略称を決める
4. `RQ-BK-[内容略称]` を採番し、要件定義書の業務課題一覧へ登録する
5. 対応する `RQ-BZ-*` を付与する
6. 関連する機能要件に、対応する `RQ-BK` を付与する

### RQ-EF を採番するとき

1. 業務課題を解決したときに見込める効果を、効果の種類（Hard Saving、Soft Saving、NWC、Cost Avoidance、TCO Savings）に分ける
2. 効果の種類と対象を表す内容略称を決める
3. `RQ-EF-[内容略称]` を採番し、要件定義書の見込み経営効果の表へ登録する。見込み（金額・時間など）と算定根拠を書く
4. 効果を生む `RQ-BK-*` を 1 つ以上付与する

### RQ-FT・RQ-UI・RQ-EX・RQ-OP を採番するとき

1. 要件定義書の該当する節の表（機能一覧と業務ルール、画面一覧と帳票・出力ファイル、外部連携、運用要件）に 1 行ずつ書く
2. 内容略称をカテゴリ別命名規則に従って決める
3. 対応する `RQ-BK-*` を、同じ行に 1 つ以上書く

### RQ-DT を採番するとき

1. データ要件を「対象データ」「扱い（保持・連携・保護）」「制約」で具体化する
2. 内容略称を名詞先頭で決める
3. `RQ-DT-[内容略称]` を採番し、要件定義書のデータ章へ登録する
4. データ章の各要件（4-1 のデータ要件、4-2 の業務エンティティ、4-4 の状態遷移）に `RQ-DT-*` を付与する。4-2 のデータ項目はエンティティの内訳なので ID を付けない
5. 対応する `RQ-BK-*` を 1 つ以上付与する

### RQ-NF を採番するとき

1. 非機能要件を「測定可能な目標値」で具体化する
2. 内容略称を名詞先頭で決める
3. `RQ-NF-[内容略称]` を採番し、要件定義書の非機能要件章へ登録する
4. 非機能要件章の各要件項目（利用者の種別とアクセス経路、性能、利用人数、可用性、移行性、セキュリティ）に `RQ-NF-*` を付与する
5. 対応する `RQ-BK-*` を 1 つ以上付与する

### RQ-TS を採番するとき

1. テスト用利用シナリオを「何を検証するか」で具体化する
2. 内容略称を動詞先頭で決める
3. `RQ-TS-[内容略称]` を採番し、要件定義書のテスト用利用シナリオ章へ登録する
4. 各テスト用利用シナリオに `RQ-TS-*` を付与する
5. 「検証する要件ID」に、そのシナリオが確かめる `RQ-FT`・`RQ-UI`・`RQ-EX`（必要なら `RQ-NF`）を書く
6. 対応する `RQ-BK-*` を 1 つ以上付与する

### 新しい DS-* を採番するとき

1. DS カテゴリを、「要件カテゴリと設計 ID の対応先」に従って選ぶ
2. DS 内容略称を、設計要素そのものを表す名前で決める（クラスならクラス名、関数なら関数名をケバブケースにする）。要件の略称は付けない
3. 対応する RQ-* を、設計書の「要件と設計の対応表」の章に 1 行で書く。複数の要件を受けるなら同じ行にカンマ区切りで並べる

### 変更管理ルール

| 変更の種類 | 対応 |
|---|---|
| 要件の**意味が変わる**場合 | 旧 ID を `.history/` 配下の変更記録内で `deprecated` としてマーク → 新 ID で新要件を登録 |

- `deprecated` となった ID は、実装後に `isdd-build` の実装後レビューが変更を正本へ反映するときに `docs/requirements.md` と `docs/detail_design.md` から削除する
- これらのドキュメントは常に現在有効な ID のみを記載する
- 要件 ID を差し替えても、設計要素の中身が変わらなければ設計 ID は変えない。変えるのは「要件と設計の対応表」の行だけで、変更設計書では旧い対応の行を [削除]、新しい対応の行を [追加] にする。設計要素の中身が変わるときは、旧設計 ID を [削除]、新しい設計 ID を [追加] にし、実装時に `docs/trace_map.md` の行も新しい設計 ID に書き換える
