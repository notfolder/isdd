## 分かったこと

- 仕様の質問の差を生んでいたのは要件定義書でした。同じコード・同じテスト・同じ README でも、要件定義書があると 15〜19 点増え、増えた分の大半は「なぜそうしたか」です。前の「42 点と 62 点」は成果物一式の比較でしたが、文書だけを変えた今回も、文書なし 43〜47 点、要件定義書つき 62 点でした。
- 設計書が増やしたのは、設計の決まりとその理由を問う質問だけでした（16 点中 +4.7）。仕組みや直す場所は、この規模（コード約 1,700 行）ではコードから読み取れました。設計書の効き目は、この測り方では小さく出ました。
- README に理由が写っていると、その分だけ文書なしの点が上がりました（理由 0.0 → 3.7 点）。README は要件定義書の一部の代わりになります。
- 文書に逆のことが書いてあっても、コードとテストを一緒に渡した読み手は、文書の誤った値を事実として答えませんでした（24 件中 0 件）。前の報告で見込みとして書いた「古くて誤った文書を渡せば、正しいコードを不具合と判定する」は、仕様の質問では起きませんでした。不具合の判定では確かめていません。
- 不具合の判定は、正しさの拠り所が 1 つあれば足りました。拠り所は要件定義書、設計書、テストのどれでもよく、この評価では要件定義書に固有の上乗せは「判断できない」が 2 件減ることと、誤りが出なくなることでした。

## 限界と、確かめていないこと

- 材料は 1 本（isdd が作った備品の貸出管理、依頼 10 回分）です。ほかの題材や、もっと大きいコードでは確かめていません。
- 読み手は AI（Opus 5.5）だけです。Haiku と人では確かめていません。
- 測ったのは、できあがった文書を読む側の出来です。文書を作る途中で不備を見つける価値、作る費用は測っていません。
- 設計書は実装と一緒に更新されたものです。実装の前に設計したことで防げた不具合は、この評価では分かりません。
- 答えが無い質問は全条件で満点になり、条件を見分けられませんでした。答えは無いがもっともらしい推測ができる質問にしないと、差は出ないと見ています（見込みで、確かめていません）。
- 逆のことが書いてある文書は、数字 3 つを文書全体で置き換え、履歴の決まりを 3 か所で書き換えたものです。文書の中で一貫して誤っています。コード・テスト・README の 3 つが正しい値で一致している条件なので、テストや README も古い場合は確かめていません。
- 不具合の判定は、古い文書の 2 条件では回していません。依頼者のレビュー（計測 7）と、60 機能の影響範囲（計測 8）もやり直していません。
- 足した 14 問の正解は、材料を読んで 1 人（AI）で決めました。根拠の場所は `questions4.json` に残してあります。人の確認はしていません。
- 元の README には「期限の延長は今は受け付けない」という古い行が残っていて、同じ README の後ろの節と食い違っています。4 条件に同じく入っています。
