# ヒアリングへの固定回答（isdd 群、計測 3: FeatureBench / mlflow）

ユーザーは不在。質問にはこのファイルの回答で答え、ここに無いことは依頼の文章（REQUEST.md）と既存コードから最も単純に決めて進める。承認（逆引きした正本の確定、変更要件の確定、設計の承認、技術選定、E2E の実行手段、実装と正本の確定）はすべて与えられたものとして進め、止まらない。

- 既存のコードベース（mlflow、数千ファイル）があり、isdd の文書が無ければ、まず isdd-reverse-engineering で正本を作る。逆引きの範囲は、REQUEST.md の Interface Description に出てくるファイルが属するパッケージ（例: `mlflow/claude_code/`）だけでよい。リポジトリ全体は読まない。正本の要件定義書・設計書もその範囲に限る（「対象外」と書く）。
- 正本があれば、REQUEST.md の依頼は既存のコードへの変更要求として isdd-spec の変更フロー（変更要件定義書 → 変更設計書）で進め、isdd-build で実装し、実装後レビューで正本に反映する。対象のパッケージが正本に無ければ、変更要件定義書の中で「新しい範囲」として足してよい。
- 外部連携: 無い（依頼の範囲ではネットワークに出ない）。帳票・画面・バッチ: 無い。利用者: このライブラリを使う開発者。
- 業務課題・目的: REQUEST.md の Task Statement のとおり。見込み効果: 算定しない。
- 非機能: 既存のとおり。性能の目標は無い。
- 技術選定: 既存のとおり（Python、既存の依存だけ。新しいライブラリは足さない）。
- テストの実行: コンテナ `fb-isdd` の中で `docker exec fb-isdd bash -lc 'cd /testbed && /opt/miniconda3/envs/testbed/bin/python -m pytest <path>'`。E2E は、公開インターフェースを呼ぶ pytest を `e2e/` に置き、同じ方法で回して JUnit XML を `e2e/results/` に出す。既存の tests/ は変更しない。
- 対応表の粒度: function。`isdd-setup` の `--src` は対象のパッケージのディレクトリ（例: `mlflow/claude_code`）だけにする。依存の規則: 無ければ「無い」でよい。
- 要件の除外: 無し。Interface Description に挙がった関数・クラスはすべて、書かれたシグネチャどおりに実装する。それ以外は作らない。
- 既存コードの変更範囲: Interface Description のファイルだけ。他の既存の挙動は変えない。
- 変更フローでの範囲の判断（計測 3 で止まった点、2026-11-05 追記）: 復元した関数を呼ぶ側の import 行の追加など、呼び出し側の整合に必要な最小の変更は依頼の範囲内。依頼の範囲外の既存の不具合は直さず、正本に現状として書く。完了チェックが README.md の「起動方法」の節を求めるときは節を足してよい。対応表チェッカーの `--src` に足せないディレクトリ（設計に無いファイルが多い）は足さず、正本に「対象はそのファイルだけで走査範囲に含めない」と書いて進める。
