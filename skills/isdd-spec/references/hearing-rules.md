# ヒアリングのルール

仕様スキル（isdd-spec）と逆引きスキル（isdd-reverse-engineering）で、ユーザーに質問するときに使う。
ユーザーは IT に詳しいとは限らない前提で聞く。

## 質問の出し方

- 聞くことが複数あるときは、まず問いどうしに依存があるかで出し方を分ける。
  - 依存がある（前の答えで次の問いや選択肢が変わる）→ 1 問ずつ順に聞く。例: 業務課題が決まる前に個別の要件は聞けない。外部連携の有無が決まる前に連携先の詳細は聞けない。
  - 依存が無い → 問いに番号（1, 2, 3…）を付け、1 回の応答でまとめて出す。ユーザーは「1A, 2B」のように一度で答えられる。往復の回数が減り、ユーザーが全体を見て判断できるため。
- まとめて出すときも、各問いだけを読んで判断できるように、何を決める問いか・選ぶと何が変わるかを問いごとに書く。
- まとめて出す問いは、同じ章や同じ話題（1 つの画面、1 つの連携先など）のものにする。話題が離れた問いを混ぜると、ユーザーが前提を取り違えるため。
- ユーザーが一部の問いにだけ答えたら、答えの無い問いを次の応答でもう一度出す。推測で埋めない。
- 具体的な選択肢を複数示し、最初に出すときから、問いごとに選択肢を次の表で書く（列: 案、内容、メリット、デメリット、複雑さ、根拠）。
  - メリットとデメリット
  - 複雑さ（C=1〜5。下の「複雑さの算定」で決める）と、どの評価軸が効いているか
  - 最小案との関係（最小案 / 条件付きで妥当 / 過剰）
- 推奨は問いごとに 1 つにし、「業務課題を満たす中で複雑さが最小の選択肢」を推奨する。表の下に「推奨: 〇〇（理由を一文）」と書く。
- 実行環境に選択肢を提示するツールがあれば使う（例: VS Code Copilot の `vscode_askQuestions`、Claude Code の `AskUserQuestion`、opencode の `question`）。無ければ選択肢をテキストで並べる。
- 専門用語を避け、業務の言葉で聞く。「MVP」という語はユーザーに使わず、「業務課題を満たす中で複雑さが最小の案」と言う。

## 言葉の意味を確定する

- ユーザーが業務語を使ったら、意味を推測で決めず、その語を使う問いへ進む前に確認する。推測した意味で書いた要件は、設計と実装まで誤りを広げるため。
- 新しいドメイン用語が出たら、要件定義書の用語集に書いて意味が確定してから次の質問に進む。

## システムの形態ごとの確認項目

要件定義書のシステムの形態に合わせて、次を確認する。未確定の項目があるうちは、要件定義を完了にしない（設計でインターフェースを組み立てられないため）。

| 形態 | 確認単位 | 確認項目 |
|---|---|---|
| GUI | 画面ごと | 画面の目的、主要要素（ボタン、一覧、入力欄など）、入力項目、表示項目、エラー時の見え方 |
| CUI | コマンドごと | コマンドの目的、引数とオプション、出力（標準出力・ファイル）、終了コード、エラー時の表示 |
| Web API | API ごと | API の目的、利用者（どのシステムか）、入力、出力、エラー時の応答 |
| バッチ | 処理ごと | 処理の目的、起動のきっかけ（時刻・出来事）、処理の対象、結果の出力先、失敗したときの扱い（再実行、通知） |

## 複雑さの算定

### 評価軸（各 0〜2 点）

- データ変更量: スキーマ変更、移行、整合性考慮の有無
- 画面/操作追加量: 新規画面数、操作分岐数、説明負荷
- 外部連携負荷: 連携先数、認証、失敗時ハンドリング
- 非機能制約負荷: 応答時間、可用性、セキュリティ要件の厳しさ
- 運用変更負荷: 監視、アラート、手順追加、教育コスト

### 複雑さレベル

5 軸の合計点 T（0〜10 点）から複雑さレベル C を決める。

| T | C |
|---|---|
| 0〜1 | 1 |
| 2〜3 | 2 |
| 4〜6 | 3 |
| 7〜8 | 4 |
| 9〜10 | 5 |

### 同点時の優先順位

同じ C の場合は、次の順で小さいものを優先する。

1. 外部連携が少ない
2. データ変更が少ない
3. 画面/操作追加が少ない
4. 運用変更が少ない

## 推奨より複雑な案が選ばれたとき

ユーザーが推奨以外、または C がより高い案を選んだら、「最小案では満たせない業務上の理由は何か」を確認する。この確認は、その答えで後の問いが変わるので、ほかの問いとまとめずに単独で出す。

- 理由が具体的になれば、選ばれた案で確定し、ユーザーが述べた理由をそのまま、要件定義書の該当する要件の「この要件が無いと何が困るか」列に書く。
- 理由が具体的にならなければ、最小案と選ばれた案の違い（複雑さと、それぞれで業務に起きること）をもう一度示し、ユーザーに選び直してもらう。最終的にはユーザーの選択に従い、同じ列に「ユーザーの選択（理由: ユーザーが述べた言葉をそのまま）」と書く。理由が無ければ「ユーザーの選択（理由は特に無い）」と書く。エージェントがもっともらしい理由を作って書かない。複雑な案を選んだ経緯を、設計や後の変更で確かめられるようにするため。
