# isdd ドキュメント作成ルール

isdd で作る仕様書・設計書のすべてに適用する。

## 書き方

- コード例は書かず、処理を日本語で具体的に書く。コードを書くと実装の写しになり、設計判断が読み取れなくなるため。yaml・json の設定例と、起動・テスト実行のコマンド 1 行は書いてよい。
- 将来の拡張案、実装スケジュール、実装フェーズは書かない。今回作るものだけを書いた文書にするため。
- 仕様や実装の選択肢を残さず、1 つに決めて書く。選択肢が残ると、実装者が判断を推測することになるため。
- Markdown で書き、複雑な説明には mermaid の図を付ける。

## ID の書き方（読みやすさのため）

- 要件 ID と設計 ID は、表の専用列（`RQ-ID`、`DS-ID`、`対応要件ID` など）に書く。
- 本文の文章の中には ID を書かない。文章では要件名や設計要素名（「注文作成機能」「OrderService クラス」）で呼ぶ。
- 図（mermaid）の中にも ID を書かない。ノード名は要素名にする。
- ID はバッククォートで囲む（例: `` `RQ-FT-CREATE-ORDER` ``）。

## 作成・修正した後のレビュー

文書を作成・修正したら、次を確認して直し、確認結果をユーザーに報告する。各スキルのレビュー項目はこれに追加して確認する。

1. 内容に矛盾がないか
2. 冗長な記述がないか
3. このルールを満たしているか
