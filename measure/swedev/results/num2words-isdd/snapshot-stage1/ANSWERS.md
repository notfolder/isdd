# ヒアリングへの固定回答（isdd 群、計測 2: SWE-Dev）

ユーザーは不在。質問にはこのファイルの回答で答え、ここに無いことは依頼の文章（REQUEST.md の PRD）と既存コードから最も単純に決めて進める。承認（逆引きした正本の確定、変更要件の確定、設計の承認、技術選定、E2E の実行手段、実装と正本の確定）はすべて与えられたものとして進め、止まらない。

- 既存のコードベースがあり、isdd の文書（docs/requirements.md など）が無ければ、まず isdd-reverse-engineering で正本を作る。逆引きの範囲は、PRD の FOLDER STRUCTURE に出てくるファイルが属するパッケージ（src のディレクトリ）だけでよい。テスト・配布設定・ドキュメントは対象外。コードベース全体を細かく読む必要は無い（大きければファイル単位の役割の要約で足りる）。
- 正本があれば、REQUEST.md の依頼は既存のコードへの変更要求として isdd-spec の変更フロー（変更要件定義書 → 変更設計書）で進め、isdd-build で実装し、実装後レビューで正本に反映する。
- 外部連携: 無い。帳票・画面・バッチ: 無い（ライブラリ）。利用者: このライブラリを使う開発者。
- 業務課題・目的: PRD の MODULE DESCRIPTION のとおり。見込み効果: 算定しない。
- 非機能: 既存のとおり。性能の目標は無い。
- 技術選定: 既存のとおり（Python、既存の依存だけ。新しいライブラリは足さない）。
- E2E の実行手段: ローカルで `python -m pytest`。このライブラリでは、公開関数を呼ぶ pytest のテストを E2E として扱い、`e2e/` に置いて JUnit XML を `e2e/results/` に出す。既存の tests/ は変更しない。
- 対応表の粒度: function。依存の規則: 無ければ「無い」でよい。
- 要件の除外: 無し。PRD に挙がった関数・メソッドはすべて実装する。PRD に無い機能は作らない。
- 既存コードの変更範囲: PRD に挙がったファイルの、挙がった関数・メソッドの追加だけ。他の既存の挙動は変えない。
