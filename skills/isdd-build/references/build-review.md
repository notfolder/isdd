# 実装後レビューの段階（isdd-build）

変更フローの変更を正本へ反映し、要件・設計・実装の差分を見つけて、正本（`docs/requirements.md`・`docs/detail_design.md`・`docs/trace_map.md`）を整合した状態に戻す手順。
正本に実装していない変更を重ねない。変更要件定義書と変更設計書を正本へ反映するのは、この段階だけが行う（isdd-spec と実装の段階は正本を書き換えない）。新規フローでは反映する変更は無く、実装が原因の差分だけを扱う。
スキルを使わずに直されたコードを正本と対応表に取り込むときも、この段階から始める。

## 扱う範囲

- 変更フローの変更要件定義書・変更設計書の正本への反映と、実装が原因の要件・設計の差分を扱う。変更要件定義書と変更設計書で確定した内容は、判定し直さない。
- 更新先は `docs/requirements.md`、`docs/detail_design.md`、`docs/trace_map.md` と、反映後に消す `docs/active_change` だけ。`change_requirements.md` と `change_detail_design.md` は変更の記録として残し、書き換えない。
- 見つけた差分を、新しい変更要件に回さない。正本を直接直す（正本と実装のずれを残さないため）。
- `docs/proposals.md` は実装中の一時ファイル。正本へ反映したか「反映不要」と決めたかにかかわらず、完了時に削除する。
- 証跡ファイルは残さない。完了時に正本だけが最新になっている状態にする。


## 入力

- 実装差分（直近のコミット差分、またはワークツリーの差分）
- `docs/requirements.md`、`docs/detail_design.md`
- `docs/trace_map.md`（無ければ未作成として扱い、このスキルの中で作る）
- `docs/proposals.md`（ある場合）
- `docs/active_change`（変更フローの場合。進行中の変更のディレクトリを指す）と、そのディレクトリの `change_requirements.md`・`change_detail_design.md`


## 手順

1. 対象コード、要件定義書、詳細設計書、直近の差分を読む。`docs/proposals.md` があれば読む。`docs/active_change` があれば変更フローなので、それが指すディレクトリの `change_requirements.md` と `change_detail_design.md` も読む。
2. 実装差分の影響範囲をまとめる。
3. 要件 ID と設計 ID の対応を確かめる。

   ```bash
   python3 .agents/skills/isdd-build/scripts/rq_ds_link_checker.py docs/requirements.md docs/detail_design.md
   ```

   このチェッカーが見るのは、要件定義書と設計書の文書間の対応だけ。「実装にあるのに要件が無い」ことや、「`change_requirements.md` の要求が正本に反映されていない」ことは検出できないので、合格しても手順 4 以降を続ける。変更フローでは、正本への反映前なので変更分の未対応は出ない。
4. 対応表とコードのずれを確かめる。変更フローでは `docs/active_change` があるので、`check.sh` は変更設計書を正本に重ねて判定する。

   ```bash
   bash scripts/isdd/check.sh
   ```

   - エラー（対応表が指す関数がコードに無い、DS-ID が設計書に無い）は、改名・削除の反映漏れなので、対応表を直す。
   - 警告「コードにあって対応表に無い」は、スキルを使わずに追加されたコードの可能性があるので、手順 6 の未マッピング一覧に入れる。
   - 警告「設計書にあって対応表に無い」は、未実装か登録漏れかをコードで確かめる。登録漏れなら対応表に足し、未実装ならユーザーに示す。
5. 変更フローの場合は、変更要件定義書と変更設計書を正本へ反映する。
   - 反映する前に、`change_requirements.md`、`change_detail_design.md`、`docs/proposals.md`、実装差分を突き合わせ、変更設計どおりに実装されているかを確かめる。実装されていない [追加] の設計要素があれば反映せず、実装の段階に戻すようユーザーに伝えて止まる（正本に作っていない仕様を書かないため）。
   - 変更要件定義書と変更設計書は確定済みの変更なので、ユーザーへの聞き直しは要らない。反映する要件 ID と設計 ID の一覧（追加・削除）を示してから反映する。
   - `docs/requirements.md`: [追加] 要件を該当章へ足し、[削除]（`deprecated`）要件とその ID を消す。業務課題一覧と、業務課題と要件の対応表を変更後の状態にする。技術制約（1-1）に変更があれば書き換える。
   - `docs/detail_design.md`: [追加] 設計要素を該当章へ足し、[削除] 設計要素とその ID を消す。変更設計書の「11-1. 除外要件」の行を `docs/detail_design.md` の 11-1 に書き写す（書き写さないと、正本どうしのチェックで除外した要件が未マッピングになるため）。
   - 正本には [追加] [削除] の区分を書かない。正本は現在有効な内容だけを持つ。
   - 両文書を全章通読し、変更前の挙動を前提にした本文（例: 「固定文字列を出力するのみ」「データを保持しない」といった説明、旧関数名・旧画面名への言及、構成図、処理フロー、用語定義）も書き換える。ID の表が新しくても、本文が旧仕様のままなら未反映とみなす。
   - 正本に既に入っている ID（isdd v2.0.0 で変更設計の確定時に反映済みのもの）は、二重に足さない。
   - 反映が終わったら `docs/active_change` を削除する。以後の `check.sh` は正本だけで判定する。
6. 実装の全関数・処理から逆にたどり、対応表に設計 ID が無いもの、対応する要件 ID が `docs/requirements.md` に無いものを未マッピング一覧にする。チェッカーが合格していても行う。
   応答には Markdown の見出し `### 未マッピング一覧` を置き、その直下に次の表を出す。太字の行は見出しの代わりにならない。列名は下の表の見出し行をそのまま写し、省略も言い換えもしない（「実装要素」ではなく「実装要素（修飾名）」）。該当が無い場合も見出しと表を出し、行に「該当なし」と書く（下の「該当が無い場合」の形）。ユーザーが表で 1 件ずつ判断できるようにするため、文章だけで済ませない。

   | 実装要素（修飾名） | 対応表の DS-ID | 設計書に DS-ID があるか | 対応する RQ-ID | 要件定義書に RQ-ID があるか | 状態 |
   |---|---|---|---|---|---|
   | `src/hello.py::HelloWorldPrinter.get_hello_message` | `DS-FN-GET-HELLO-MESSAGE` | あり | `RQ-FT-GET-HELLO-MESSAGE` | なし | 要件未定義 |

   該当が無い場合（見出しの直下を文章の「該当なし」だけにしない）:

   | 実装要素（修飾名） | 対応表の DS-ID | 設計書に DS-ID があるか | 対応する RQ-ID | 要件定義書に RQ-ID があるか | 状態 |
   |---|---|---|---|---|---|
   | 該当なし | ― | ― | ― | ― | ― |

   状態は「要件未定義」「設計未定義」「対応表未登録」「整合」のどれか。「整合」の行は省略してよいが、未マッピングの行は省略しない。
7. 未マッピングを 1 件ずつユーザーに聞き、「削除」「修正」「分割」「統合」「追加」のどれにするかを決める。
8. 決めた内容を `docs/requirements.md` に反映する。反映後は手順 5 と同じく全章を通読し、旧仕様を前提にした本文を書き換える。
9. 更新した要件 ID を設計書へ伝え、設計を直す。新しい設計 ID に対応するコードを `docs/trace_map.md` に登録する。
10. `rq_ds_link_checker.py` と `bash scripts/isdd/check.sh --strict` をもう一度実行し、出力で未整合ゼロ（エラー 0 件・警告 0 件）を確かめる。変更フローでは `docs/active_change` を消した後に実行し、出力に「進行中の変更」の行が無い（正本だけで判定した）ことも確かめる。未整合が残れば手順 6 に戻る。
11. `docs/proposals.md` があれば削除する。


## 完了条件

- `rq_ds_link_checker.py` と `bash scripts/isdd/check.sh --strict` の実行ログを応答に載せ、未整合がゼロ（対応表のエラー 0 件・警告 0 件を含む）
- Markdown の見出し `### 未マッピング一覧` と、手順 6 の 6 列（列名は省略しない）の表を応答に載せた（該当なしの場合も）
- 要件の更新が必要だった場合、1 件ずつ聞き直して反映し、設計 ID と対応表に伝えた
- `docs/proposals.md` が無い
- 変更フローの場合、変更要件定義書と変更設計書の [追加] [削除] が正本に反映され、`change_requirements.md` の要求意図と正本の内容（ID の表だけでなく、データ章・用語定義・概要などの本文も）が矛盾していない
- `docs/active_change` が無い


## 報告

次を報告する。

- 変更フローの場合、正本へ反映した要件 ID・設計 ID の一覧と、書き換えた本文の箇所
- 実装後逆引き整合の結果。未整合が無ければ「未整合ゼロ」と書く（チェッカーごとの件数だけで済ませない）。残っていれば、その一覧
- 未マッピング一覧
- 要件の更新結果と、設計 ID・対応表への伝播結果

未整合が残っていて設計を直す必要がある場合は、`isdd-spec` で設計を直すよう案内する。

未整合がゼロになった場合は、確定した成果物と今後の進め方を案内する。

- `docs/requirements.md`: 確定した要件定義書。次の変更要件定義の起点になる
- `docs/detail_design.md`: 確定した詳細設計書。要件との対応をたどれる
- `docs/trace_map.md`: 設計 ID とファイル・クラス・公開関数の対応表。コードに ID を書かずに仕様とコードを結ぶ
- `e2e/`: 実装を検証する E2E テスト。詳細設計書 8-4 の実行コマンドで動かす（外部連携がある場合は mock と real の 2 モード）
- 新しい要求は `isdd-spec` から始める（変更フローになる）
- 既存の実装にバグや仕様誤りが見つかった場合も、`isdd-spec` で要件と設計を直してから `isdd-build` で直す
