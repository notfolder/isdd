# 実装の段階（isdd-build）

設計の設計要素を 1 対 1 でコードに落とし、設計 ID とコードの対応を対応表 `docs/trace_map.md` に記録する手順。

`docs/active_change` があれば変更フローの実装中で、その 1 行目が変更のディレクトリ（`.history/[YYYYMMDD]-[タスク名]/`）を指す。正本には変更がまだ反映されていないので、そのディレクトリの `change_requirements.md` と `change_detail_design.md` を正本に重ねて読む（有効な設計は「正本 ＋ [追加] − [削除]」）。`scripts/isdd/check.sh` も同じように重ねて判定する。

## 守ること

- 要件 ID と設計 ID の正本は `docs/requirements.md` と `docs/detail_design.md` だけ。変更フローの実装中は、これに変更要件定義書と変更設計書を重ねたものを設計として扱う。
- コードに要件 ID・設計 ID を書かない。コメントは言語の流儀に従った通常のドキュメントコメント（処理の説明、引数、戻り値）だけにする。対応は対応表で持つので、コードに書くと二重管理になり、ずれるため。
- ID を採番しない。設計書に無い設計要素が要るとわかったら、コーディングを止めて `docs/proposals.md` に提案を書き、`isdd-spec` で設計を直してから再開する。採番を isdd-spec に限ると、設計書と対応表の ID が常に一致するため。
- 止まったら、ユーザーが `isdd-spec` を起動するまで待つ。このスキルの中で `isdd-spec` を実行したり、要件・設計の文書、変更要件定義書・変更設計書・`docs/active_change` を自分で作ったりしない。「進めてください」と言われても、それは `isdd-spec` の起動ではない。要件と設計はユーザーへのインタビューと承認で決めるもので、実装の段階が推測で作ると、ユーザーが決めていない仕様が実装されるため。
- 正本（`docs/requirements.md`・`docs/detail_design.md`）と、変更要件定義書・変更設計書は書き換えない。`docs/active_change` も消さない。実装中に見つけた要件・設計の不足や矛盾は `docs/proposals.md` に書く。正本への反映は実装後レビューの段階（build-review.md）が行い、完了時に `docs/proposals.md` を削除する。
- 削除された要件・設計に対応するコードは削除し、対応表の行も削除する。
- 既存コードがある場合、設計の範囲外のロジックは変えない。


## 対応表

書式と粒度は trace-map-rules.md に従う。要点:

- 列は「DS-ID」「修飾名」「備考」の 3 列。
- 修飾名は `ファイルパス`（DS-MD）、`ファイルパス::名前`（クラス・関数）、`ファイルパス::クラス名.名前`（メソッド）。
- 載せるのはファイル、クラス、公開関数・メソッド（粒度 `class` ではファイルとクラス）。アンダースコア始まりの内部関数、ダンダーメソッドは載せない。E2E テストは `DS-TS` の行でテスト関数に結ぶ（設計書 8-2 の各 `DS-TS-*` に 1 行以上）。
- 設計書第 7 章の「実現する設計 ID」列にある `DS-IF`・`DS-BT`・`DS-EV`・`DS-SC` は、そのファイルのクラスや関数として載せる。
- 設計書第 7 章の依存の規則が `scripts/isdd/dependencies.json` と合っているか確かめ、違えば設計書に合わせて書き直す。`check.sh` の依存チェックに違反が出たら、コードを直す（規則を緩めない。規則を変えるのは設計の見直し）。
- クラス・公開関数・ファイルを追加、改名、削除したら、同じ作業の中で対応表を更新する。


## 外部連携のコード

設計書に外部連携がある場合は、設計書の 4-1・8-2〜8-4 と `external/[システム名]/docs/research.md` に従って、次を作る。

- 連携ライブラリ（`external/[システム名]/src/`）: 外部 API のエンドポイントを 1 対 1 でメソッドにする薄いラッパー。業務ロジックを入れない。既存ライブラリを採用した設計なら、その公開インターフェースを包む。コードには要件 ID・設計 ID を書かず、設計書の `DS-MD-*`・`DS-IF-*` を対応表に登録する（`isdd-setup` の `--src` に `external/[システム名]/src` を含める）。業務ロジックが外部 API のライブラリを直接 import しないことは、`check.sh` の依存チェックが確かめる。
- モック（`external/[システム名]/mock/`）: 設計書 8-4 のモック方式で作る。E2E 側からはシンボリックリンクで参照し、リンクも Git で管理する（モックの正本を 1 か所にするため）。モックとテストは対応表に載せない。
- E2E の 2 モード: mock モードと real モードを、テスト実行コマンドで切り替えられるようにする（実行形態がコンテナなら docker compose のプロファイルも）。実装時の必須ゴールは mock モードの全件通過。real モードは手動実行だけを必須にする。
- テスト環境を作るスクリプトは bash を基本にし、複雑な処理はプロジェクトの言語か Python で書く。
- 接続情報は `.env` から読む。値をコード・テスト・ログに書かない。

## 手順

tasks.md がある場合は、そのタスクを上から順に進める。無い場合は次の順に進める。

1. `docs/requirements.md` と `docs/detail_design.md` を読み、要件 ID と設計 ID をすべて把握する。`docs/active_change` があれば、変更要件定義書と変更設計書も読み、[追加] の要素を実装し、[削除] の要素に対応するコードと対応表の行を消す。
2. 設計要素（DS-MD、DS-CL、DS-FN、DS-IF、DS-BT、DS-EV）ごとに実装する。
3. 実装したファイル・クラス・公開関数を `docs/trace_map.md` に登録する。対応がわからない要素はユーザーに確認する。
4. 対応表の整合を確かめる。エラーも警告も 0 件になるまで、コードか対応表を直す。`check.sh` は対応表チェック、依存チェック、受け入れ判定（E2E の結果の JUnit XML と `DS-TS` 行の照合）を順に実行するので、先に 8-4 の実行コマンドで E2E を回して `e2e/results/` に結果を出しておく。

   ```bash
   bash scripts/isdd/check.sh --strict
   ```

5. 要件 ID と設計 ID の対応を確かめる。問題があれば終了コード 1 になる。

   ```bash
   python3 .agents/skills/isdd-build/scripts/rq_ds_link_checker.py docs/requirements.md docs/detail_design.md
   ```

   変更フローでは、変更要件定義書と変更設計書の組み合わせも確かめる（`[変更のディレクトリ]` は `docs/active_change` の 1 行目）。

   ```bash
   python3 .agents/skills/isdd-build/scripts/rq_ds_link_checker.py [変更のディレクトリ]/change_requirements.md [変更のディレクトリ]/change_detail_design.md --base docs/requirements.md
   ```

6. 実装完了の条件を確かめる。要求される項目は `scripts/isdd/completeness.json`（詳細設計書の実行形態・認証・外部連携から生成）で決まる。

   ```bash
   python3 scripts/isdd/implementation_completeness_checker.py .
   ```

   - 出力の冒頭の「実行形態 / 認証 / 外部連携」が詳細設計書と合っているか確かめる。違えば `isdd-setup` を正しい値で再実行する。
   - FAIL があれば直して再実行する。よくある FAIL と直し方:
     - `docker-compose.yml が見つかりません`（実行形態がコンテナの場合だけ出る）→ docker-compose.yml を作る
     - `e2e/ ディレクトリが存在しません` → 詳細設計書 第 8 章のとおり E2E テストを `e2e/` に作る
     - `README.md に不足があります` → 起動方法（認証がある場合は初期ユーザー情報も）を README.md に書く
     - `docs/trace_map.md が見つかりません` → 対応表を作る
7. 詳細設計書 8-1 の実行コマンドで単体テストと結合テストが全件通ること、第 9 章の起動方法で起動または実行できること、8-4 の実行コマンドで E2E テストが全件通ること（外部連携がある場合は mock モード）を確かめる。
8. 要件・設計との対応漏れが無いかを見直し、ユーザーに報告する。


## 完了条件

次をすべて満たしてから完了を報告する。満たしていない項目があれば、完了ではなく残っている項目として報告する。

- `bash scripts/isdd/check.sh --strict` がエラー 0 件・警告 0 件（対応表チェック、依存チェック、受け入れ判定のすべて。受け入れ判定は 8-2 の全 `DS-TS` が合格、全要件が実装済み）で、実行ログを応答に載せた
- `rq_ds_link_checker.py` が問題 0 件で、実行ログを応答に載せた
- `implementation_completeness_checker.py` が全項目 OK で、実行ログを応答に載せた
- 詳細設計書 8-1 の実行コマンドで単体テストと結合テストが全件通った
- 第 9 章の起動方法で起動または実行できた（実行形態がコンテナなら `docker compose up`）
- E2E テストが `e2e/` にあり、詳細設計書 8-4 の実行コマンドで全件通った（外部連携がある場合は mock モード）
- `README.md` に「起動方法」がある（認証がある場合は「初期ユーザー」も）
- コードに `要件ID:` `設計ID:` `RQ-` `DS-` を含むコメントが無い
