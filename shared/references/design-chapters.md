# 詳細設計書の必須章立て

詳細設計書（変更設計書を含む）は、次の章をすべて持つ。
各章の設計要素（モジュール・クラス・関数・インターフェース・データモデル・バッチ・イベント・テスト・運用）には、ID 定義（id-definitions.md）に従って `DS-*` ID を付与する。ID の無い設計要素は、要件と実装の両方から追跡できないため書かない。
要件 ID ごとにどの種類の設計 ID で受けるかは、ID 定義の「要件カテゴリと設計 ID の対応先」に従う。
該当するものが無い節も、節を消さずに「〜は無い」と書く（確認漏れと区別するため）。

## 1. 言語・フレームワーク・アーキテクチャの選定

言語、フレームワーク、DB 製品、実行形態（サーバー / コンテナ / クライアント）は、既定値を持たない。
要件定義書の「1-1. 技術制約」と要件（システムの形態、画面一覧、非機能要件、外部連携、データ量）を根拠に、候補を比較して選ぶ。

**選定の手順**

1. 要件定義書の技術制約と要件から、判断軸ごとに「この案件で効く条件」を書き出す。
2. 判断軸を満たす候補を言語・フレームワーク・DB それぞれ 2〜3 件挙げる。既存コードベースがある場合はその技術を第一候補にする。
3. 候補ごとにインターネットで公式情報を調べる。確認する内容は、現在保守されているか、最新の安定版とサポート期限、ライセンス、配備先で動くか、必要な外部連携の公式クライアントがあるか。モデルの知識は古い可能性があり、保守終了やライセンス変更を見落とすため、記憶だけで決めない。
4. 候補を比較表にし、選定結果と理由をユーザーに提示して承認を得る。承認前に設計の他の章へ進まない。
5. 承認結果を設計書に記録する。

**インターネット調査ができない場合**

- 検索ツールや取得ツールが使えない環境では、推測で選ばずに止まる。
- 「インターネット調査ができないため技術選定を確定できない」とユーザーに報告し、ユーザーが公式情報を提供するか、未調査のまま進める許可を出すまで待つ。
- 未調査のまま進める許可が出た場合は、比較表の出典列に「未調査（ユーザー承認: 日付）」と書く。

**判断軸**

| 判断軸 | 見るもの | 効き方 |
|---|---|---|
| 既存資産との整合 | 既存コードの言語・フレームワーク、既存 DB | あれば最優先。別技術にするには業務上の必須理由が要る |
| チームの技術 | 扱える言語、禁止技術 | 扱えない技術は候補から外す |
| 配備先 | OS、コンテナ可否、クラウドのサービス、ネットワーク制約 | 配備先で動かない候補は外す |
| 認証と認可の境界 | SSO の要否、画面・機能・データ単位の認可、監査ログ、インターネット公開 | 境界が厳しいほど、フロントとバックを分けて認証を一箇所に集められる構成が有利 |
| 画面の規模 | 画面数、画面遷移の複雑さ、状態管理の有無、再利用部品の有無 | 単一画面で軽量なら画面を素早く作れる枠組み、多画面で状態が多いならコンポーネント指向の枠組み |
| データの規模と構造 | 件数の初期値と増加率、参照関係の複雑さ、検索と集計の有無、同時更新 | 少量で単純ならファイルベースの DB、それ以外は本格的な RDB。DB が不要なら「DB は必須ではないため、DB 設計は行わない」と明記 |
| 外部連携 | 連携先の API 形式、公式クライアントの有無 | 公式クライアントがある言語が有利 |
| ライセンスとコスト | 有償の可否、OSS ライセンス、ランニングコスト | 制約に合わない候補は外す |
| 保守性 | 保守状況、サポート期限、情報の多さ | 保守が止まっている候補は外す |

**選定結果に書く項目**

- 判定日時
- 技術制約の要約（要件定義書 1-1 の内容）
- 判断軸ごとの該当有無と理由（表形式）
- 候補の比較表（候補 / 判断軸ごとの評価 / 出典 URL / 確認日）
- 最終選定結果（言語、フレームワーク、DB、実行形態）と選定理由（業務要件との対応）
- ユーザー承認の記録（承認日）

**フロントエンドとバックエンドを分ける構成を選んだ場合に書く項目**

- フロントエンド：ビルド後の静的配信方式
- バックエンド：リバースプロキシの配置と API の経路（パスの接頭辞を 1 つに決めて統一する）
- 認証境界の位置

## 2. システム構成

- コンポーネント一覧（要件を根拠に表形式）
- システム全体構成図（mermaid）
- 各コンポーネントの役割と機能
- コンポーネント間インターフェースとデータフロー
- ネットワーク構成図（mermaid）: サーバー・コンテナ・外部連携など、ネットワーク越しの通信がある構成の場合だけ書く。無ければ「ネットワーク越しの通信が無いため、ネットワーク構成図は書かない」と書く

## 3. データ設計

### 3-1. データモデル

- DB が必要かを判定し、理由を書く。DB 製品は第 1 章の選定結果に従い、第 1 章で選定していない製品をここで持ち込まない
- DB を使う場合: テーブル設計（カラム、型、制約）とリレーション図（mermaid）。テーブルごとに `DS-SC-*` を付ける
- DB を使わない場合: 「DB は必須ではないため、DB 設計は行わない」と書き、扱うデータの構造（ファイルの形式、データクラスなど）を `DS-SC-*` で設計する
- カラムと入力チェックは、要件定義書 4-2 のデータ項目（必須、形式・桁、値の範囲）に対応させる

### 3-2. トランザクションと排他制御

- 要件定義書 4-3 の CRUD テーブルの備考にある、トランザクションが要る操作ごとに、トランザクションの範囲とロールバックの条件を書く
- 同時更新がある操作ごとに、排他制御の方式（楽観的 / 悲観的）と選んだ理由を書く
- 該当する操作が無ければ「トランザクション・排他制御が要る操作は無い」と書く

### 3-3. 状態遷移

- 要件定義書 4-4 の状態遷移ごとに、状態の持ち方（どのデータのどの値か）と、遷移を行う処理（`DS-FN-*`）を表と状態遷移図（mermaid）で書く
- 許されない遷移を求められたときの扱い（エラーの種類）を書く
- 状態を持つエンティティが無ければ「状態を持つエンティティは無い」と書く

## 4. アーキテクチャ設計

### 4-1. 外部設計

- 利用者向けインターフェース（`DS-IF-*`）。要件定義書のシステムの形態に合わせて書く
  - GUI: 画面一覧（各画面の要素と機能）、画面遷移図、AA モックアップ
  - CUI: コマンド・引数・設定の一覧表
  - Web API: API の一覧（パス、メソッド、用途）
  - 帳票・出力ファイル: 要件定義書 3-1 の出力ごとの形式と項目
- インターフェース仕様: 各 `DS-IF-*` について、次を表で書く
  - 入力と、そのバリデーション（要件定義書 4-2 のデータ項目と 3-2 の業務ルールのどれに当たるか）
  - 出力
  - エラー仕様（エラーの種類、利用者への見え方または戻り値、業務ルール違反のときの扱い）
- 外部システム連携（一覧、インターフェース、データフロー図）
  - 要件に外部連携がある場合、`external/[システム名]` の調査結果をもとに設計する
  - 外部連携先は `external/[システム名]/src` の連携ライブラリを通して呼ぶ設計にする。直接呼ぶと、E2E テストでモックに切り替えられなくなるため
- 外部 DB 連携（一覧、インターフェース、データフロー図）

### 4-2. 内部設計

- 処理フロー図（mermaid）
- 各処理の役割と機能
- 必要に応じたバッチ設計（フロー図、役割。バッチごとに `DS-BT-*`）

## 5. クラス設計

クラス設計は SOLID 原則に沿わせる。

- 全クラス一覧と役割
  - SOLID 原則への適合状況を表で明示
- クラスの責務、主要属性、主要メソッド
- クラス図（mermaid）
- システム内メッセージ一覧と役割
- メッセージフロー図（mermaid）

## 6. エラーハンドリングとセキュリティ設計

- エラーハンドリング: 想定エラーの一覧と、それぞれの扱い（利用者への見え方、ログ、処理の続行か中止か）
- 認証: 方式。SSO の場合は IdP と認証の流れ。認証が無い場合は「認証は無い」と書く
- 認可: ロールと操作の権限表。画面・機能・データのどの単位で制御するか。認可が無い場合は「認可は無い」と書く
- 監査ログ: 要件定義書の運用要件にある場合、記録する操作と項目、保存先と保存期間、改ざん防止の方法
- その他のセキュリティ対策: 要件定義書の非機能要件（利用者の種別、アクセス経路など）から必要になるもの

## 7. コード設計

- ソースコードのディレクトリ構成（AA）：ファイル名は含めない
- 各ディレクトリ配下のファイル名、役割、含まれるクラスの一覧表：ソースファイル（テストファイルを除く）ごとに 1 つ `DS-MD-*` を付け、同じ行にそのファイルが実現するほかの設計 ID も書く。対応表はファイル単位の行を `DS-MD-*` で持つので、`DS-MD-*` の無いファイルは実装時に「未登録ファイル」の警告が消えないため
- 言語・フレームワークに応じたコーディング規約表
- コードには要件 ID・設計 ID を書かない。設計 ID とコードの対応は実装時に `docs/trace_map.md`（対応表。書式は trace-map-rules.md）へ記録する旨を書く

## 8. テスト設計

### 8-1. テストの種類と方針

- テストの種類（単体・結合・総合・E2E）ごとの目的と方法
- 実装するテストケース
  - 全モジュールの単体テスト
  - 全機能要件の結合テスト
  - システム全体の総合テスト
- 単体テスト・結合テストの実行コマンド（実装スキルと tasks.md はこのコマンドをそのまま使う）
- 非機能要件の検証: 実現する設計要素が無い非機能要件（利用人数の前提、応答時間の目標など）は、それを確かめるテストを `DS-TS-*` で設計して対応させる

### 8-2. E2E テストのシナリオ

- 要件定義書のテスト用利用シナリオ（`RQ-TS-*`）を 100% 網羅する
- シナリオごとに `DS-TS-*` を付け、次の表で書く

  | DS-ID | 対応要件ID | 目的 | 前提条件 | 手順 | 期待結果 |
  |---|---|---|---|---|---|

- 外部連携がある場合は `mock` モードと `real` モードの 2 モードを設計し、すべてのシナリオを両モードで実行対象にする。外部連携が無い場合はモードを設けない

### 8-3. E2E の実行手段（第 1 章の実行形態とシステムの形態に従う）

- Web の GUI: ブラウザ自動化ツールを使う。ツールは第 1 章と同じ手順（判断軸、インターネット調査、比較表、ユーザー承認）で選び、使用するバージョンを書く
- CLI・バッチ: 実際に実行して標準出力・終了コード・出力ファイルを確かめるテストを、プロジェクトの言語のテストフレームワークか bash で書く
- Web API: 実際に API を呼び、応答を確かめるテストを書く
- デスクトップ・ライブラリ: 実行形態に合うテスト手段を第 1 章と同じ手順で選ぶ
- 実行形態がコンテナの場合は、テスト実行用のサービスを docker compose に追加する。通常起動では起動しないプロファイルにし、テストコードをマウントして即時反映できる構成にする。外部連携がある場合は `mock` / `real` の切り替えプロファイルも定義する

### 8-4. E2E の実行コマンドと運用

- E2E の実行コマンドを書く。実装スキルと tasks.md はこのコマンドをそのまま使う（例: コンテナなら `docker compose run --rm <テストサービス名> <テストコマンド>`、CLI なら `python3 -m pytest e2e` のような形）
- テスト資産はプロジェクトルートの `e2e` 配下に置く
- 外部連携がある場合、外部モックは `external/[システム名]/mock/` を正本とし、`e2e` 側はシンボリックリンクで参照する（Git 管理下に置く）。モードの切り替えはテスト実行コマンドで行う（コンテナなら docker compose プロファイルも）
- テスト環境を作るスクリプトは原則 bash で書き、複雑な処理はプロジェクトの言語か Python を使う
- コンテナの場合、テスト実行時の URL は compose 内のサービス名で書く
- 実装時・CI の必須ゴールは E2E の全件通過（外部連携がある場合は `mock` モードで）。`real` モードの E2E は手動実行だけを必須にする
- テストが失敗したら修正と再実行を繰り返し、全件成功まで続ける方針を書く

## 9. 運用設計

起動・初期化・設定・バックアップの各設計要素に `DS-OP-*` を付ける。

- 起動方式は第 1 章で選定した実行形態に従う。選定していない方式をここで持ち込まない
  - コンテナ: docker compose で起動する。compose の定義ファイルとサービス構成を書く
  - CLI: 実行手順（インストール、実行コマンド、引数）を書く
  - コンテナを使わないサーバー・デスクトップ・ライブラリ: 配備先に合わせた起動またはインストールの手順を書く
- DB スキーマや初期ユーザーなどの初期化が要るなら、起動時に自動で行う。認証が無い場合は「初期ユーザーは無い」と書く
- 設定値・環境変数の一覧（名前、用途、既定値、必須か）。パスワードなど秘密情報の値は書かない。外部連携の接続情報は `.env` から読む前提で変数名だけを書く
- バックアップと復旧: 要件定義書の運用要件にある場合、対象、頻度、手順、復旧の確認方法
- データ移行: 要件定義書の非機能要件に移行性の要件がある場合、移すデータ、変換の規則、手順、移した後の確認方法
- 可用性: 要件定義書の非機能要件に可用性の要件がある場合、それを満たす構成と、止める作業（更新など）の手順
- 起動方法と操作説明を README.md に書く旨を書く

## 10. ログ・監視・アラート・障害対応設計

各設計要素に `DS-OP-*` を付ける。

- ログ: 要件定義書の運用要件に従う。不要なら「ログの設計は必須ではないため、ログの種類と内容の記述は行わない」と書く
- 監視・アラート: 要件定義書の運用要件に従う。不要なら「監視・アラートの設計は必須ではないため、監視・アラートの内容と対応方法の記述は行わない」と書く
- 必要な場合は、内容と対応方法を表で書く
- 障害対応: 想定する障害（外部連携先の停止、ディスク不足など）ごとに、検知の方法、対応手順、復旧の確認方法を書く。運用要件に監視・アラートが無い場合も、利用者が障害に気づいたときの対応を書く

## 11. 要件と設計の対応表

設計書の最後に、すべての設計 ID と対応する要件 ID を 1 行ずつ並べた表を置く。各章の表に対応要件 ID 列があっても省略しない。`rq_ds_link_checker.py` はこの表の各行で `DS-*` と `RQ-*` が同じ行にあることを対応の根拠にする。

| DS-ID | 対応要件ID |
|---|---|
| `DS-MD-...` | `RQ-FT-...` |

- 1 つの設計要素が複数の要件に対応するときは、要件 ID をカンマ区切りで同じ行に書く
- この表に無い設計 ID、どの行にも現れない要件 ID（`RQ-BK`・`RQ-BZ`・`RQ-EF` と、11-1 の除外要件を除く）は、未マッピングとして扱う

### 11-1. 除外要件

ユーザーの承認を得て設計から外した要件を、次の表で書く（手順は requirement-exclusion.md）。`rq_ds_link_checker.py` は、この節にある要件 ID には設計 ID の対応を求めない。外した要件が無ければ「除外要件は無い」と書く。

| RQ-ID | 除外理由 | 吸収先 DS-ID | 承認日 |
|---|---|---|---|
