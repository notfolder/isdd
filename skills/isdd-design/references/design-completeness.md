# isdd 設計完全性制約

詳細設計スキル（isdd-design、isdd-change-design）が、作った設計書の抜けを確かめるチェックリスト。

---

## 完全性チェック項目

満たしていない項目は、不足としてユーザーに示し、設計書を直す。

### データ（第 3 章）

- 要件定義書 4-2 の全エンティティにデータモデル（`DS-SC-*`）があり、データ項目の必須・形式・値の範囲がカラムと入力チェックに反映されているか
- エンティティと画面、API、クラスの対応関係が明確であるか
- データ整合性（PK、FK、業務制約）が定義されているか
- 要件定義書 4-3 の CRUD テーブルの備考にある操作に、トランザクションの範囲・ロールバック条件・排他制御の方式があるか（3-2）
- 要件定義書 4-4 の全遷移に、状態の持ち方と遷移を行う処理、許されない遷移の扱いがあるか（3-3）

### インターフェース（第 4 章）

- システムの形態（GUI・CUI・Web API・バッチ）と帳票・出力ファイルのすべてに `DS-IF-*` があるか
- 各インターフェースの入力・バリデーション・出力・エラー仕様があり、要件定義書 3-2 の業務ルールがすべてどこかのバリデーションかエラー仕様に現れているか

### セキュリティ・監査（第 6 章）

- 認証、認可（ロールと操作の権限表）、監査ログが設計されているか（無い場合は「無い」と書いてあるか）

### 運用・監視（第 9・10 章）

- 起動、初期化、設定値・環境変数の一覧、バックアップ（要件にある場合）に `DS-OP-*` があるか
- ログ、監視、アラート、障害対応が定義されているか

### テスト（第 8 章）

- 全機能に対応する正常系、異常系テストが設計されているか
- 要件定義書の全テストシナリオ（`RQ-TS-*`）に E2E シナリオ（`DS-TS-*`）があるか
- 実現する設計要素が無い非機能要件に、確かめるテスト（`DS-TS-*`）があるか

### コード品質

- 同一意味処理の重複実装が排除され、再利用方針が明記されているか

### 要素の削除

- 削除可能な設計要素を列挙しているか
- 削除しても要件を満たす要素は実際に削除しているか

### ID 付与

- 全ての設計要素に `DS-*` ID が付与されているか（ID なし要素がある場合は不足として修正する）
- 各要件が、ID 定義の「要件カテゴリと設計 ID の対応先」に合う種類の設計 ID で受けられているか
- 承認を得て外した要件が「11-1. 除外要件」に承認日つきで書かれているか
- ID は表の専用列にあり、本文の文章や図の中に書かれていないか

### 技術選定

- 言語・フレームワーク・DB・実行形態が、要件定義書の技術制約と判断軸を根拠に選ばれているか
- 候補の比較表に出典 URL と確認日があるか（未調査の場合はユーザー承認の記録があるか）
- 選定結果にユーザー承認の記録があるか

---

## 外部連携時の確認

- 要件に外部連携があるのに、`external/[システム名]` の内容が完全でない場合は、不足としてユーザーに指摘する
