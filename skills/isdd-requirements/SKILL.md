# isdd-requirements — インタビュー駆動 要件定義スキル

ユーザーから必要な情報を段階的に聞き出し、矛盾が無く、業務課題を満たす最小の要件定義書を `docs/requirements.md` に作る。
後続の設計スキルはこの文書だけを根拠に設計するので、推測で埋めた箇所を残さない。

## このスキルのファイル

参照ファイルはこのスキルの `references/`、チェッカーは `scripts/` にある。下のコマンドは `.agents/skills/` に入れた場合のパスで書いている。別の場所（`.claude/skills/`、`.github/skills/`、ホーム配下など）に入れた場合は、この SKILL.md があるディレクトリに読み替える。

| ファイル | 使う場面 |
|---|---|
| `references/hearing-rules.md` | すべての質問（質問の出し方、複雑さの算定、用語の確定、システムの形態ごとの確認項目） |
| `references/requirements-chapters.md` | 要件定義書の章立て |
| `references/id-definitions.md` | 要件 ID の採番 |
| `references/document-rules.md` | 文書の書き方と、作成後のレビュー |
| `scripts/rq_integrity_checker.py` | 要件 ID の整合チェック |

## 開始ゲート

要件ヒアリングに入る前に、次の 2 問をこの順に 1 問ずつ聞く。答えによって、このスキルで進めるか、別のスキルを先に使うかが変わるため。

- 質問 1（外部連携の有無）: A. ある / B. ない / C. 不明
- 質問 2（既存ソースコードと isdd の運用）: A. 既存ソースコードはない / B. 既存ソースコードがあり、isdd で運用している / C. 既存ソースコードがあり、isdd で運用していない / D. 既存ソースコードがあり、isdd の運用は不明
  - 必要なら「isdd とは、要件定義書と詳細設計書を先に確定し、要件 ID と設計 ID で仕様と実装の対応を追跡する開発方式です」と補足する。

分岐:

- 質問 1 が A → `isdd-external-precheck` を先に実行し、完了を確認してから要件ヒアリングへ進む。
- 質問 2 が A → このスキルの要件ヒアリングへ進む。
- 質問 2 が B → `isdd-change-req` へ案内する（要件定義書が既にあるため、変更要件として扱う）。
- 質問 2 が C か D → `isdd-reverse-engineering` を先に実行するよう案内する。完了すると要件定義書と設計書が揃うので、このスキルには戻らず、新しい要求は `isdd-change-req` で進める。

2 問の答えと先行スキルの完了が揃うまでは、要件の本編を聞かず、不足している答えの確認だけを行う。

## 業務の問題と業務課題の確定

要件ヒアリングの最初に、業務の問題と業務課題を確定する。isdd ではすべての要件を業務課題に結びつけるので、業務課題が決まる前に機能・画面・外部連携・非機能の質問を始めない。
問題は業務のあるべき姿と現状のギャップ、課題（業務課題）は問題を解決するために取り組むアクションやテーマを指す（`references/requirements-chapters.md` の「用語: 問題と課題」）。

1. 作りたいアプリをユーザーが既に話していればそれを使う。話していなければ「一言で言うとどのようなアプリですか？」と聞く。
2. 対象業務を `RQ-BZ-*` で採番し、業務ごとにあるべき姿と現状を聞いて、そのギャップを業務の問題として確定する。できるだけ KPI の数値で聞く。
3. 問題ごとに、解決のために取り組むことの候補をいくつか示し、ユーザーが取り組む業務課題を特定する。
4. 業務課題を `RQ-BK-*` で採番して確定する。
5. 業務課題を解決したときの見込み経営効果を聞き、`RQ-EF-*` で採番する。算定できなければ、その理由を書く。

## ヒアリング

`references/hearing-rules.md` に従って聞く。加えて次を守る。

- `references/requirements-chapters.md` の章ごとに、内容が確定するまで一問一答で聞いてから書く。
- 技術制約（既存コードベースの言語、配備先、チームが扱える技術と禁止技術、ライセンスとコスト、性能と規模の目安）を確認し、要件定義書の「1-1. 技術制約」に記録する。「特に無い」も回答として記録する。言語や製品名をこちらから勧めない（選定は設計スキルが候補を比較して行うため）。
- 分からない点が残る限り質問を続ける。

## 要件の書き方

- ID は `references/id-definitions.md` に従って付ける。業務は `RQ-BZ-*`、業務課題は `RQ-BK-*`、見込み経営効果は `RQ-EF-*`、機能と業務ルールは `RQ-FT-*`、画面・帳票・Web API は `RQ-UI-*`、外部連携は `RQ-EX-*`、データ章の各要件は `RQ-DT-*`、非機能要件は `RQ-NF-*`、運用要件は `RQ-OP-*`、テスト用利用シナリオは `RQ-TS-*`。
- `RQ-BK` と `RQ-BZ` 以外の要件には、対応する `RQ-BK-*` を 1 つ以上、同じ表の行に書く。結びつかない要件は、削除するか業務課題を追加してから定義し直す。
- 業務課題と要件の対応表（`RQ-BK-*` と `RQ-*` の対応）を作る。
- 各要件に「この要件が無いと何が困るか」を書く。説明できない要件は削る。
- 同じ目的の要件は 1 つにまとめる。
- 将来の拡張、一般論、ベストプラクティスは書かない。今回の業務課題に要るものだけにする。
- 文書の書き方は `references/document-rules.md` に従う。

## 網羅性チェック

要件定義書を作成・修正したら、次を確認し、不足があれば直す。

- 業務の問題（あるべき姿と現状のギャップ）を書き、すべての業務課題に解決する問題があるか
- 業務エンティティをすべて列挙し、エンティティごとにデータ項目（必須、形式・桁、値の範囲）を書いたか
- 各エンティティの CRUD テーブル（4-3）を作ったか
- マスタに当たるエンティティに管理機能があるか
- 機能カテゴリ（業務機能 / マスタ管理 / 共通（認証・認可・ログ）/ 運用 / 外部連携）を検討したか
- 状態を持つエンティティの状態遷移（4-4）を定義したか
- 業務ルール（3-2）、帳票・出力ファイル（3-1）、外部連携（3-3）、非機能要件の可用性と移行性、運用要件（第 6 章）を、無い場合も「無い」と書いたか
- 機能と画面・ユーザーフローの対応を確かめたか
- 削除できる要件を列挙し、削除しても業務が成り立つ要件を実際に削除したか
- すべての要件項目に `RQ-*` ID があるか
- すべての `RQ-BK-*` に対応する要件が 1 件以上あり、`RQ-BK`・`RQ-BZ` 以外のすべての要件に対応する `RQ-BK-*` があるか

## 外部連携の整合

外部連携がある場合は、要件定義書の初版を書いた後に `isdd-external-research` を実行し、`docs/requirements.md` を入力として外部仕様と突き合わせる。
不足・矛盾・過剰が見つかったら要件定義書を直し、網羅性チェックをやり直す。不整合が残っているうちは設計へ進まない。

## 整合チェック

要件定義書ができたら、次を bash で実行する。

```bash
python3 .agents/skills/isdd-requirements/scripts/rq_integrity_checker.py docs/requirements.md
```

チェッカーは、カテゴリの書式違反、`RQ-BK` との対応が無い要件、対応する要件が無い `RQ-BK` を報告する。問題があれば要件定義書を直して再実行し、0 件になってからレビューへ進む。実行ログは応答に載せる。

## レビュー

`references/document-rules.md` のレビュー項目に加えて、次を確認する。問題があれば直してから報告する。

1. 網羅性チェックをすべて満たしているか
2. 外部連携がある場合、`isdd-external-research` の整合確認の結果を反映したか
3. 業務課題と要件の対応が両方向に成り立っているか

問題がなければ完了とし、`docs/requirements.md` として保存する。

## 次のステップ

完了を報告するときに、次のスキルを提案する。

- 外部連携がある場合: `isdd-external-research` で外部仕様との整合を確認する
- 外部連携がない場合: `isdd-design` で詳細設計書を作る
