# Codex による isdd の評価方法レビュー

作成日: 2026-11-23

## 対象と結論

`SUMMARY.md` の計測 1〜12、`EVALUATION-REVIEW.md` の見直しと決定、`.history/BACKLOG.md`、関連する採点・実行コードを確認した。結果の全件再集計や評価の再実行は行っていない。

既存の見直しが示す「測れていない価値があるため、isdd の縮小判断を保留する」という方向は妥当である。一方、題材を追加するだけでは、採点の失敗を得点に混ぜる問題や、少数の試行から一般化する問題は解消しない。まず採点の成立条件と比較の単位を明確にし、既存結果の表現も測定範囲に合わせる必要がある。

## 評価できる点

- 隠しテストによる成果物の評価、変更後の退行確認、費用と時間の記録を組み合わせている。手法に固有の文書の有無だけで成果を判定していない。
- 一文つき・数文つきの比較群があり、手順全体と簡単な指示の差を検討できる。弱いモデルや外部の題材も一部で試している。
- `ripple/README.md` には参照実装と意図的に誤りを入れた実装によるテスト確認の記録がある。過去の不備や少ない試行回数も報告されている。

## 指摘と提案

### 1. 採点できなかった結果が、得点や退行の集計に混ざりうる【高】

根拠: `measure/score.py` は pytest の終了コードを記録せず、JUnit の testcase 名だけをキーにする。同名テストは上書きされ、収集失敗やタイムアウトで XML が無い場合は 0 件になる。`measure/run.py` の採点呼び出しは終了コードを確認せず、退行の計算では後段で消えたテストを退行に含めない。`measure/docval/qa.py` は採点者の応答を解析できなければ空の判定にし、欠けた点数を 0 点として中央値を計算する。

影響: テストの未実行、環境不良、採点者の出力失敗が成果物の不合格や低得点に見えたり、退行が見逃されたりする。実際に公表済みの数値が影響を受けたかは、今回確認していない。

提案: テストをファイル・クラス・名前を含む識別子で記録し、期待件数との差、pytest の終了状態、XML 欠落を検出する。採点失敗とアプリの起動・機能不良を区別し、前者は未採点として再採点する。退行表には未実行を別に出す。LLM 採点は全項目の形式と値を検証し、有効な 3 判定が揃わなければ点数を確定しない。既存結果にもこの検査を適用して影響を確認する。

### 2. 結論が注記より強い箇所が残っている【高】

根拠: `SUMMARY.md` 2 章は縮小判断の保留を追記しているが、同じ章に「省ける所が多くあります」、6 章に「出来は同じ」「効き目の芯」とある。計測 3 の isdd は 2 回、一文つきは 3 回で、計測 4 の数文つきと isdd は各 1 回である。`EVALUATION-REVIEW.md` も「画面の機能テストだけ」と記す一方、計算 API や文書の読み取り評価も実施している。

影響: 限定的な結果が、isdd 全体での同等性や不要な手順の特定として読まれる。回数の少なさは同等性を示す根拠にもならない。

提案: 2 章と 6 章の断定を「この題材・指標・試行では差が確認できなかった」に揃え、各数値に回数を併記する。「画面の機能テストだけ」は該当する題材に限定する。計測 9 は isdd を実行していないことを結論にも添える。見直し文書の「測定済み」も、その題材と指標に限る表現にする。

### 3. 新題材を対照群の結果だけで選ぶと比較が偏る【高】

根拠: `EVALUATION-REVIEW.md` 5 章とバックログは、まずバイブコーディングと一文つきで試し、両方が落ちる題材だけ isdd を回す方針である。

影響: 対照群が偶然低得点だった題材だけを選ぶと、後から isdd に有利な差が見えやすい。isdd の効果が大きい題材を探す探索には使えても、選択後の差をそのまま一般的な効果として扱えない。

提案: 先行試行は題材とテストの不備を直す探索として明示し、選択条件と結果を残す。本比較は修正後に全群を新しい独立した試行で実行し、採否と集計の規則を事前に固定する。落ちた題材だけでなく、選ばれなかった題材と理由も報告する。

### 4. 試行数と統計の解釈を揃える【高】

根拠: `SUMMARY.md` は多数の条件が 1〜3 回であることを示す一方、計測 2 の 0.7% を「偶然で出る確率」と記している。記事では 4 件以下と 5 件以上という区切りを使っているが、その区切りを観測前に決めたかは今回確認できない。

影響: 個々のテストは同じアプリから得た結果で独立試行ではなく、少数の実行や事後に選んだ区切りから得た値は不確実性を過小評価しうる。p 値は仮定した帰無モデルの下で観測結果以上に極端な結果が出る確率であり、仮説が偶然である確率ではない。

提案: 独立したアプリ生成 1 回を比較の単位にし、各回の結果、群の差、試行数と不確実性を示す。主要指標、比較、区切り、検定方法と追加実行の停止条件を事前に記録する。探索的な集計はその旨を明記し、0.7% の算出方法と事前指定の有無を検証してから表現する。

### 5. 新題材の採点が、目指す価値とずれるおそれがある【中】

根拠: A1 は業務課題の解決、A2 は不要機能の削減を測る計画だが、A2 の指標には機能数・行数・費用が挙がる。既存の `measure/score.py` の overbuild はソース量や Python の公開関数などの数であり、不要機能かどうかは判定していない。

影響: 必要な機能を省けば機能数や行数は減る。技術や実装方法の違いによる行数差も、作りすぎの証拠にはならない。

提案: 依頼者の真の課題と必要な成果を事前に定義し、業務シナリオの達成を必須条件とする。その上で、課題に不要と判定した機能の実装有無、必要な機能の欠落、費用を別々に報告する。行数は参考値として扱う。依頼者役に一貫した事情と回答基準を与え、必要な仕様が質問に対して得られることを確認する。

### 6. 群の実行条件と手順の実施状況を区別する【中】

根拠: `measure/run.py` は isdd 群を、スキル呼び出しまたは文書・スクリプトの存在で `valid` と判定する。既存成果物を使う試行ではファイルの存在だけでは今回の段で手順を実行した証拠にならない。完了状態は別に記録される。AI-DLC 群も記録の存在と完了状態は別である。

影響: 群に割り当てられたこと、実際に手順を使ったこと、完了したことが混同されると、失敗例の除外や成功率の解釈に偏りが生じる。

提案: 割り当て、スキルの可視性、実際の呼び出しや文書更新、完了、採点可否を別項目として残す。全割り当て試行を主集計に含め、未完了や環境障害を理由別に表示する。手順を実施できた試行だけの集計は補助として併記し、除外規則を事前に決める。モデル、版、依頼者役、制限時間、待機時間を群ごとに記録する。

### 7. LLM 採点の一致だけでは正しさを保証できない【中】

根拠: `measure/docval/qa.py` は同一モデルに 3 回採点させ、中央値を採る。`measure/webgen/grader-prompt.md` も 3 判定の集計を指定している。

影響: 同じモデルと基準の判断は共通の偏りを持ちうる。多数決はばらつきを減らしても、基準や正解自体の誤りを直せない。

提案: 条件を伏せた回答の一部を人が独立に採点し、判定の一致率と不一致の事例を記録する。採点者間のばらつきと、正解・基準の修正履歴も残す。機械的に判定できる項目は固定テストを優先する。

## 既存の決定との関係

A1・A2 を最初に扱い、次に模擬 HTTP API による B1 を扱う決定は維持できる。上記の指摘 3 のとおり、対照群だけの先行実行は探索と位置づけ、本比較では全群を独立に実行する。新しい評価が終わるまで isdd を軽くする判断を保留する方針にも賛成する。
