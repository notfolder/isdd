# isdd-change-req — インタビュー駆動 変更要件定義スキル

既存の要件を理解したうえで、今回の変更要求に必要な要件を [追加] と [削除] で整理し、矛盾の無い変更要件定義書を作る。

## このスキルのファイル

参照ファイルはこのスキルの `references/`、チェッカーは `scripts/` にある。下のコマンドは `.agents/skills/` に入れた場合のパスで書いている。別の場所（`.claude/skills/`、`.github/skills/`、ホーム配下など）に入れた場合は、この SKILL.md があるディレクトリに読み替える。

| ファイル | 使う場面 |
|---|---|
| `references/hearing-rules.md` | すべての質問（質問の出し方、複雑さの算定、用語の確定、システムの形態ごとの確認項目） |
| `references/requirements-chapters.md` | 変更要件定義書の章立て |
| `references/id-definitions.md` | 要件 ID の採番と変更管理 |
| `references/document-rules.md` | 文書の書き方と、作成後のレビュー |
| `scripts/rq_integrity_checker.py` | 要件 ID の整合チェック |

## 書く場所と書かない場所

- 変更要件は `.history/[YYYYMMDD]-[タスク名]/change_requirements.md` にだけ書く。タスク名は `20250115-add-user-profile` の形にする。
- 既存の `docs/requirements.md` はこのスキルでは書き換えない。正本への反映は `isdd-change-design` が変更設計の確定時に行う。ここで書き換えると、設計前に正本と変更記録の 2 か所が食い違うため。

## 開始ゲート

変更要件のヒアリングに入る前に、外部連携の有無を聞く（A. ある / B. ない / C. 不明）。

- A → `isdd-external-precheck` を先に実行し、完了を確認してから進む。
- B か C → 変更業務課題の確定へ進む。

答えと先行スキルの完了が揃うまでは、変更要件の本編を聞かない。

## 業務の問題と変更業務課題の確定

作業を始めたら `docs/requirements.md` を読んで既存要件を理解する。そのうえで、変更要件の最初に、今回の変更で解決する業務の問題と業務課題を確定する。業務課題が決まる前に個別の要件を聞かない（要件はすべて業務課題に結びつけるため）。
問題は業務のあるべき姿と現状のギャップ、課題（業務課題）は問題を解決するために取り組むアクションやテーマを指す（`references/requirements-chapters.md` の「用語: 問題と課題」）。

1. 変更したい機能や目的をユーザーが既に話していればそれを使う。話していなければ「一言で言うと今回どのような変更ですか？」と聞く。
2. 対象業務のあるべき姿と現状を聞き、そのギャップを業務の問題として確定する。できるだけ KPI の数値で聞く。
3. 問題ごとに、解決のために取り組むことの候補をいくつか示し、ユーザーが取り組む業務課題を特定する。
4. 変更対象の業務課題を `RQ-BK-*` で採番して確定する。
5. 見込み経営効果に変わりがあるかを聞き、追加する効果は `RQ-EF-*` で採番する。

## ヒアリング

質問を出す前に `references/hearing-rules.md` を読み、それに従って聞く。とくに次を守る。

- 1 回の応答で聞くのは 1 問だけにする。
- 選択肢を伴う質問は、最初に出すときから次の表で示す（複雑さの算定のしかたは hearing-rules.md の「複雑さの算定」）。表が無いと、ユーザーは選択肢の重さを比べられないため。

  | 案 | 内容 | メリット | デメリット | 複雑さ（C=1〜5） | 根拠（効いている評価軸） |
  |---|---|---|---|---|---|

  表の下に「推奨: 〇〇（理由を一文）」と書く。推奨は、業務課題を満たす中で複雑さが最小の案にする。
- ユーザーが推奨より複雑な案を選んだら、次の順に進める（hearing-rules.md の「推奨より複雑な案が選ばれたとき」）。
  1. 次の応答では他の質問をせず、「最小案では満たせない業務上の理由は何か」を尋ね、最小案と選ばれた案の違い（複雑さと、それぞれで業務に起きること）を示す。
  2. 理由が具体的でなければ、選び直しを 1 度だけ求める。それでも同じ案なら、ユーザーの選択に従う。
  3. その要件の「この要件が無いと何が困るか」列に、「ユーザーの選択（理由: ユーザーが述べた言葉をそのまま）」と書く。理由が無ければ「ユーザーの選択（理由は特に無い）」と書く。エージェントが理由を作って書かない（後で経緯を確かめるとき、本当の理由と区別できなくなるため）。
- 選んだ案の詳細（置き場所、書き方など）を確かめるときも、選択の質問とは別の応答で 1 問ずつ聞く。
- システムの形態ごとの確認項目（hearing-rules.md）を聞き、変更要件定義書の該当する節に書く。CUI ならコマンドごとに、引数、出力、終了コード、エラー時の表示を書く。

あわせて次を守る。

- `references/requirements-chapters.md` の章ごとに、内容が確定するまで一問一答で聞いてから書く。
- 技術制約に変更があるかを確認し、変更要件定義書の「1-1. 技術制約」に記録する。変更が無ければ「変更なし。既存要件定義書 `docs/requirements.md` 1-1 を参照」と書く。言語や製品名をこちらから勧めない（選定は設計スキルが行うため）。
- 分からない点が残る限り質問を続ける。

## 変更要件の書き方

- すべての要件項目に [追加] か [削除] を書く。「変更」という区分は使わず、変える要件は旧要件を [削除]、新要件を [追加] に分けて書く。区分が 2 つだけなら、正本へ反映するときに機械的に処理できるため。
- 要件の意味が変わる場合は、旧要件を [削除]（`deprecated`）とし、新しい `RQ-*` ID を採番して [追加] する。
- [削除] 要件には削除理由と、不要になる、または解消される `RQ-BK-*` を書く。
- [追加] 要件と、`RQ-BK`・`RQ-BZ` 以外のすべての要件には、対応する `RQ-BK-*` を 1 つ以上、同じ表の行に書く。
- ID は `references/id-definitions.md` に従う。業務は `RQ-BZ-*`、見込み経営効果は `RQ-EF-*`、機能と業務ルールは `RQ-FT-*`、画面・帳票・Web API は `RQ-UI-*`、外部連携は `RQ-EX-*`、データ章の各要件は `RQ-DT-*`、非機能要件は `RQ-NF-*`、運用要件は `RQ-OP-*`、テスト用利用シナリオは `RQ-TS-*`。
- CRUD テーブルは、変更の有無にかかわらず全エンティティ分を書く（変更の影響が他のエンティティに及んでいないかを確かめるため）。
- 変更が無い章は「変更なし。既存要件定義書 `docs/requirements.md` セクション[N] を参照」とだけ書く。
- 変更後の業務課題と要件の対応表（`RQ-BK-*` と `RQ-*` の対応）を書く。
- 変更要件は業務課題を解決するのに要る最小の単位にする。既存要件と同じ目的の要件は足さない。
- 各要件に「この要件が無いと何が困るか」を書く。将来の拡張、一般論、ベストプラクティスは書かない。
- 文書の書き方は `references/document-rules.md` に従う。

## 網羅性チェック

追加・削除する要件について次を確認し、不足があれば直す。

- 今回の業務課題に、解決する業務の問題（あるべき姿と現状のギャップ）が書いてあるか
- 業務エンティティをすべて列挙し、追加・変更するエンティティのデータ項目（必須、形式・桁、値の範囲）を書いたか
- 各エンティティの CRUD テーブル（4-3）を全エンティティ分書いたか
- マスタに当たるエンティティに管理機能があるか
- 機能カテゴリ（業務機能 / マスタ管理 / 共通（認証・認可・ログ）/ 運用 / 外部連携）を検討したか
- 状態を持つエンティティの状態遷移（4-4）に影響が無いか確かめ、変わる遷移を書いたか
- 業務ルール（3-2）、帳票・出力ファイル（3-1）、外部連携（3-3）、非機能要件（可用性・移行性を含む）、運用要件（第 6 章）への影響を確かめたか
- 機能と画面・ユーザーフローの対応を確かめたか
- 削除できる要件を列挙し、削除しても業務が成り立つ要件を実際に削除したか
- ユーザーが推奨より複雑な案を選んだ要件の「この要件が無いと何が困るか」列が、「ユーザーの選択（理由: ユーザーが述べた言葉）」または「ユーザーの選択（理由は特に無い）」になっているか（会話で記録すると伝えた内容と、文書の記述が同じか）
- すべての要件項目に `RQ-*` ID と、[追加] か [削除] の区分があるか
- [追加] 要件はすべて `RQ-BK-*` に結びつき、[削除] 要件にはすべて不要になる `RQ-BK-*` が書いてあるか
- 業務課題と要件の対応が両方向に成り立っているか

## 外部連携の整合

外部連携がある場合は、変更要件定義書の初版を書いた後に `isdd-external-research` を実行し、`change_requirements.md` を入力として外部仕様と突き合わせる。
不足・矛盾・過剰が見つかったら変更要件定義書を直し、網羅性チェックをやり直す。不整合が残っているうちは変更設計へ進まない。

## 整合チェック

変更要件定義書ができたら、次を bash で実行する。`[YYYYMMDD]-[タスク名]` は実際のディレクトリ名に置き換える。

```bash
python3 .agents/skills/isdd-change-req/scripts/rq_integrity_checker.py .history/[YYYYMMDD]-[タスク名]/change_requirements.md
```

チェッカーは、カテゴリの書式違反、`RQ-BK` との対応が無い要件、対応する要件が無い `RQ-BK` を報告する。問題があれば変更要件定義書を直して再実行し、0 件になってからレビューへ進む。実行ログは応答に載せる。

## レビュー

`references/document-rules.md` のレビュー項目に加えて、次を確認する。問題があれば直してから報告する。

1. 網羅性チェックをすべて満たしているか
2. 外部連携がある場合、`isdd-external-research` の整合確認の結果を反映したか
3. 業務課題と要件の対応が両方向に成り立っているか
4. `docs/requirements.md` を書き換えていないか

問題がなければ完了とし、`.history/[YYYYMMDD]-[タスク名]/change_requirements.md` として保存する。

## 次のステップ

完了を報告するときに、次のスキルを提案する。

- 外部連携がある場合: `isdd-external-research` で変更要件と外部仕様の整合を確認する
- 外部連携がない場合: `isdd-change-design` で変更詳細設計書を作る
