## 概要
v2.2.0（「検証する要件ID」列・受け入れ判定スクリプト・作りすぎの件数・位置づけの書き換え）を実装して公開し、isdd あり・なしの効果の計測 1（備品管理、Haiku、2 群 × 2 回 × 3 段）を試運転した。Anthropic API の月間上限で止まった最後の eval 3 場面は、Claude Code のヘッドレス実行（定額契約）で回す実行器を足して通した。

## やったこと

### v2.2.0 の実装（ブランチ `v2.2.0-acceptance` → PR #10 → main `aec36d2`）
- 要件定義書 第 7 章の表に「検証する要件ID」列を足し、`rq_integrity_checker.py` が `RQ-FT`・`RQ-UI`・`RQ-EX` の 1 本以上の `RQ-TS` への出現をエラーで求める（列の ID は `RQ-BK` 対応の構築から外す。正本では列にしか無い ID を「未定義参照」。変更要件定義書は [追加] の要件だけ）。
- 新スクリプト `acceptance_checker.py`（E2E の JUnit XML と対応表の `DS-TS` 行を突き合わせ、要件ごとに 実装済み / 不合格 / 未検証 を表で出す。`--strict` で未実行・不合格を失敗扱い、`--active-change` で変更文書を重ねる、テストディレクトリが無ければ省く、XML がコードより古ければ要再実行の警告〔2 秒の猶予〕）と `unittest_junit.py`（標準ライブラリだけの JUnit XML 書き出し）。`isdd-setup` が複製し、`check.sh` の 3 段目に組み込み、`.gitignore` に `e2e/results/` を足す。
- 実装後レビューの未マッピング一覧に「要件なし（作りすぎ）」と件数の行、「要件ごとの実装済み判定」の表。実装後レビューが正本を直す唯一の段階であることを明記し、要件を足すときは第 7 章の「検証する要件ID」にも同じ応答で足す。
- README の「背景と目的」を「文脈を持たない次の作業者への契約と、その強制」に書き換え、「向く案件・向かない案件」「段階の区切りでセッションを切り替える」を追加。
- 単体テスト 90 本（Python 3.9〜3.15）。eval の fixture 約 25 ファイルに列を足し、場面定義 12 本に新スクリプト 2 本を列挙。
- 全場面 eval で落ちた 3 場面（build の未マッピング、spec の外部連携ヒアリング、ヒアリングの作法）の原因は本文の弱さ（報告の表を出さない、正本を直さずに止まる、問いを 1 問ずつ出す、複雑な案の聞き直しをしない）。SKILL.md・build-review.md・spec-external.md を直した。

### 公開
- 差分 eval の途中で Anthropic API の月間上限（2026-12-01 に回復）に達したため、`evals/run-claude-code.py` を新設。waza の場面定義・fixture・採点基準をそのまま読み、`claude -p`（Claude Code のログイン、定額契約）で依頼と追い打ち依頼を同じセッションに送り、prompt 型の採点は同じセッションを分岐して判定を JSON で受け取る。残り 3 場面が Haiku の 1 回目で合格（1 場面 2〜3 分）。
- `gh skill publish ./skills --tag v2.2.0`、このPCのユーザーグローバルを `--pin v2.2.0` で入れ直し。

### 計測 1 の試運転（`measure/`、結果は `measure/results/REPORT.md`）
- 契約（contract.md）に基づく隠しテスト 21 本（Playwright）、段の依頼 3 本、固定回答、Agent ツール（Haiku）で各段を実行する `stage.py`、採点 `score.py`、採点し直し `rescore.py`。
- 結果: isdd 群 21/21 と 18/21、対照群 20/21 と 19/21。退行は両群 0。作りすぎ（公開関数）は isdd 40〜41、対照 51〜60。isdd 群のトークンは約 2.5〜3 倍。
- 契約が全段の画面を含んでいたため両群とも段 1 で全機能を作り、段 2・3 が検証だけになって「積み重ね」は測れていない。Sonnet の再実行は不要と判断。

### 意図的に残したもの
- `measure/run.py`（`claude -p` の無人実行）は、全権限を外す指定を含むため自動モードの分類器に止められた。`run-claude-code.py` と同じ権限指定（`acceptEdits` ＋ 許可ツールの列挙、依頼は標準入力）にすれば動く見込みだが未着手。
- waza での 3 場面の再確認は 12-01 以降に任意。

## 決定事項
- 受け入れ判定は新しいスクリプト 1 本に置き、`trace_map_checker.py` は広げない。前向きの網羅（要件が 1 本以上のシナリオに現れる）は最初からエラー（ユーザー判断 2026-11-04）。
- `e2e/results/` は git 管理外。古い XML は警告、未実行・不合格は `--strict` のときだけ失敗（pre-commit は止めない）。
- 変更要件定義書で `RQ-TS` を求めるのは [追加] の FT/UI/EX だけ。列だけの変更は [削除]・[追加] の 2 行で差し替える。
- 計測 1 は、ブランチの E2E を隠しテストとして再利用し契約を両群に渡す。対照群は段の依頼と契約だけ。両群 Haiku、各群 2 回、3 段は「台帳と閲覧 → 貸出・返却 → アカウント管理」。公開後に止まらず計測まで続ける。
- eval は API ではなく定額契約（Claude Code のログイン）でも回せるようにする（ユーザー指示 2026-11-04）。waza は API キーしか使えず、Claude Code の OAuth を他ツールへ流用するのは規約違反のため、`claude -p` を使う実行器で代替した。
