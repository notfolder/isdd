# 設計の段階（isdd-spec）

確定した要件から、要件をすべて満たし、要件に無いものを足さない最小の設計を作る手順。実装の段階（isdd-build）は設計の設計要素だけを実装するので、設計に無いものは作られず、設計にあるものはすべて作られる前提で書く。

| フロー | 入力 | 書く先 |
|---|---|---|
| 新規 | `docs/requirements.md` | `docs/detail_design.md`、`.history/[YYYYMMDD]-[タスク名]/tasks.md` |
| 変更 | `.history/[YYYYMMDD]-[タスク名]/change_requirements.md` と正本 | 同じディレクトリの `change_detail_design.md` と `tasks.md`、`docs/active_change`。正本（`docs/requirements.md`・`docs/detail_design.md`）は書き換えない |

## 1. 最小設計と要件の除外

requirement-exclusion.md に従う。要点:

- 要件（変更フローでは [追加] 要件。`RQ-BK`・`RQ-BZ`・`RQ-EF` を除く）はすべて設計に反映する。外せるのは他の要件の設計（変更フローでは既存設計も）で実現済みの要件だけで、ユーザーの承認を得て「11-1. 除外要件」に吸収先の設計 ID と一緒に書く。実装できない・矛盾する要件は、除外せずに要件を直す。
- 要件に無い設計要素は足さない。
- 設計中に要件 ID と設計 ID の未マッピングが出たら、ユーザーに聞き直して要件の文書を直し、設計に伝える。変更フローで直した要件 ID と理由は tasks.md の末尾にも書く。

## 2. 技術選定

言語・フレームワーク・DB・実行形態に既定値は無い。design-chapters.md 第 1 章の手順で、要件の「1-1. 技術制約」と要件を根拠に候補を比較して選ぶ。変更フローでは既存設計の技術を引き継ぎ、変更要件の技術制約がそれと矛盾する場合だけ選び直す。

- 候補ごとにインターネットで公式情報を調べ、出典 URL と確認日を比較表に書く。
- 検索・取得ツールが使えない環境では推測で選ばず、「インターネット調査ができないため技術選定を確定できない」と報告して止まる。ユーザーが情報を出すか、未調査のまま進める許可を出すまで他の章へ進まない。
- 選定結果をユーザーに示して承認を得る。承認の前に他の章へ進まない（技術が決まらないと他の章が書けないため）。

## 3. 外部連携の設計

外部連携がある場合は、外部連携の段階の調査レポート（`external/[システム名]/docs/research.md`）をもとに、次を決めて設計書に書く。

- **連携ライブラリの採否**: 既存ライブラリを使うか、独自の薄いラッパーにするかを、調査レポートの比較表・推奨理由・不採用理由・リスク評価（運用・法務・保守）の形でユーザーに示し、ユーザーの承認で決める。候補が 1 件でもこの形にする。独自のラッパーにする場合はその理由を書く。
  - 連携ライブラリは `external/[システム名]/src/` に置き、外部 API のエンドポイントを 1 対 1 でメソッドにする薄いラッパーにする。業務ロジックを入れない（外部仕様の変更と業務の変更が同じコードに影響するため）。
  - モジュールに `DS-MD-*`、公開インターフェースに `DS-IF-*` を付ける（design-chapters.md 4-1）。
- **モック方式**: 外部システムの性質で次から選び、ユーザーの承認で決める。モックは `external/[システム名]/mock/` に置き、`DS-TS-*` で設計する（design-chapters.md 8-4）。

  | 外部システムの特性 | 推奨方式 |
  |---|---|
  | レスポンスが静的でパターンが少ない | 固定レスポンスファイル |
  | 状態を持つ、CRUD 操作がある | ローカル HTTP サーバー |
  | 認証フローが複雑 | ローカル HTTP サーバー |
  | 複数の外部システムを同時に扱う | 既存のモックサーバーツール |
  | エラー・遅延・障害の注入が要る | 既存のモックサーバーツール |
  | DB 直結 | 検証用の DB（ファイルベースの DB の複製など） |

- **E2E の 2 モード**: mock モードと real モードを design-chapters.md 第 8 章（8-2〜8-4）に従って設計する。

## 4. 設計書の書き方

- 章立ては design-chapters.md に従う。要件との対応は第 11 章「要件と設計の対応表」（`DS-ID` と `対応要件ID` の 2 列）だけに書き、全設計 ID を 1 行ずつ並べる。各章の表に対応要件 ID の列は置かない。
- すべての設計要素に id-definitions.md に従って `DS-[種類]-[要素名]` の ID を付ける。要件の略称は付けない。どの種類の設計 ID で受けるかは、同ファイルの「要件カテゴリと設計 ID の対応先」に従う。テストファイルを除くすべてのソースファイルには、第 7 章のファイル一覧で `DS-MD-*` を 1 つずつ付ける。ID は表の専用列に書き、本文や図には書かない。
- 同じ意味の処理を 2 回作らず、共通化する前提で設計する。冗長な設計要素を列挙し、要件を満たす範囲で削除する。
- 確認が要るのは、技術選定・連携ライブラリ・モック方式の承認と、要件レベルの不足（外部連携の API 仕様、外部スキーマなど）だけにする。それ以外はユーザーに確認せず進める。
- 文書の書き方は document-rules.md に従う。

### 変更フローで足すこと

- すべての設計要素に [追加] か [削除] を書く。「変更」という区分は使わず、中身が変わる要素は旧要素を [削除]、新要素を [追加] に分けて書く。削除する要素には削除理由を書く。
- 要件 ID が差し替わっても、中身の変わらない設計要素の ID は変えない。第 11 章の対応の行だけを、旧い対応を [削除]、新しい対応を [追加] で書く。
- CRUD テーブルは、変更の有無にかかわらず全エンティティ分を書く。
- 変更が無い章は「変更なし。既存設計 `docs/detail_design.md` セクション[N] を参照」とだけ書く。
- 第 11 章には [追加] [削除] の設計 ID と対応の行を並べ、変更しない既存の設計 ID でも変更要件の要件 ID を受けるものは「変更なし（既存）」の行で書く。

設計・検証・修正を繰り返し、網羅性チェックとレビューが終わるまで続ける。

## 5. 網羅性チェック

design-completeness.md の項目をすべて確認し、不足があれば直す。変更フローでは既存設計書との整合も確かめる。

## 6. 整合チェック

設計書ができたら、次を bash で実行する。0 件になるまで設計書を直し、要件側の不足で未マッピングが出たら、requirement-exclusion.md の手順で要件の文書を直してから再実行する。実行ログは応答に載せる。

```bash
# 新規
python3 .agents/skills/isdd-spec/scripts/rq_ds_link_checker.py docs/requirements.md docs/detail_design.md
# 変更（--base に正本の要件定義書を渡すと、変更設計書が既存の要件を参照していても未定義参照にならない）
python3 .agents/skills/isdd-spec/scripts/rq_integrity_checker.py .history/[YYYYMMDD]-[タスク名]/change_requirements.md
python3 .agents/skills/isdd-spec/scripts/rq_ds_link_checker.py .history/[YYYYMMDD]-[タスク名]/change_requirements.md .history/[YYYYMMDD]-[タスク名]/change_detail_design.md --base docs/requirements.md
```

チェッカーは、対応の無い要件 ID・設計 ID、第 11 章に無い設計 ID、要件に無い要件 ID への参照を報告する（1 つの設計 ID が複数の要件 ID に対応するのは正常なので報告しない）。問題があれば終了コード 1 になる。

## 7. レビュー

document-rules.md のレビュー項目に加えて、次を確認する。問題があれば直してから報告する。

1. 冗長な設計が無いか
2. 網羅性チェックをすべて満たしているか
3. 承認の無い要件の除外が残っていないか
4. 未マッピングが出た場合、要件の文書への反映と設計への伝播が終わっているか

## 8. 保存と引き渡しの準備

1. 新規フローは `docs/detail_design.md`、変更フローは `.history/[YYYYMMDD]-[タスク名]/change_detail_design.md` として保存する。
2. 変更フローでは、`docs/active_change` に変更のディレクトリのパス（例: `.history/20250115-add-user-profile/`）を 1 行だけ書く。`isdd-build` の対応表チェックはこのファイルがあれば変更設計書を正本に重ねて判定し、実装後レビューが正本へ反映し終えたらこのファイルを消す。別の変更が登録済み（別のディレクトリを指している）なら書き換えず、先にその変更を `isdd-build` で正本へ反映するようユーザーに伝えて止まる。変更を重ねると、どの差分がどの変更のものか分からなくなるため。
3. `.history/[YYYYMMDD]-[タスク名]/tasks.md` を design-tasks-rules.md に従って作る。
