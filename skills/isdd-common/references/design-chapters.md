# 詳細設計書の必須章立て

以下の全項目を必ず含める。
各セクションに登場する全ての設計要素（クラス・API・関数・データモデル等）には、必ず `.agents/skills/isdd-common/references/id-definitions.md` に従った `DS-*` IDを付与すること。IDのない設計要素は記述しない。

### 1. 言語・フレームワーク・アーキテクチャの選定

言語、フレームワーク、DB 製品、実行形態（サーバー / コンテナ / クライアント）は、既定値を持たない。
要件定義書の「1-1. 技術制約」と要件（画面一覧、非機能要件、外部連携、データ量）を根拠に、候補を比較して選ぶ。

**選定の手順（必須）**

1. 要件定義書の技術制約と要件から、判断軸ごとに「この案件で効く条件」を書き出す。
2. 判断軸を満たす候補を言語・フレームワーク・DB それぞれ 2〜3 件挙げる。既存コードベースがある場合はその技術を第一候補にする。
3. **候補ごとにインターネットで公式情報を調べる**（必須）。確認する内容は、現在保守されているか、最新の安定版とサポート期限、ライセンス、配備先で動くか、必要な外部連携の公式クライアントがあるか。
4. 候補を比較表にし、選定結果と理由をユーザーに提示して承認を得る。承認前に設計の他の章へ進まない。
5. 承認結果を設計書に記録する。

**インターネット調査ができない場合**

- 検索ツールや取得ツールが使えない環境では、調査を省略して推測で選んではならない。
- 「インターネット調査ができないため技術選定を確定できない」とユーザーに報告し、ユーザーが公式情報を提供するか、未調査のまま進める許可を出すまで止まる。
- 未調査のまま進める許可が出た場合は、比較表の出典列に「未調査（ユーザー承認: 日付）」と書く。

**判断軸**

| 判断軸 | 見るもの | 効き方 |
|---|---|---|
| 既存資産との整合 | 既存コードの言語・フレームワーク、既存 DB | あれば最優先。別技術にするには業務上の必須理由が要る |
| チームの技術 | 扱える言語、禁止技術 | 扱えない技術は候補から外す |
| 配備先 | OS、コンテナ可否、クラウドのサービス、ネットワーク制約 | 配備先で動かない候補は外す |
| 認証と認可の境界 | SSO の要否、画面・機能・データ単位の認可、監査ログ、インターネット公開 | 境界が厳しいほど、フロントとバックを分けて認証を一箇所に集められる構成が有利 |
| 画面の規模 | 画面数、画面遷移の複雑さ、状態管理の有無、再利用部品の有無 | 単一画面で軽量なら画面を素早く作れる枠組み、多画面で状態が多いならコンポーネント指向の枠組み |
| データの規模と構造 | 件数の初期値と増加率、参照関係の複雑さ、検索と集計の有無、同時更新 | 少量で単純ならファイルベースの DB、それ以外は本格的な RDB。DB が不要なら「DB は必須ではないため、DB 設計は行わない」と明記 |
| 外部連携 | 連携先の API 形式、公式クライアントの有無 | 公式クライアントがある言語が有利 |
| ライセンスとコスト | 有償の可否、OSS ライセンス、ランニングコスト | 制約に合わない候補は外す |
| 保守性 | 保守状況、サポート期限、情報の多さ | 保守が止まっている候補は外す |

**選定結果に必須で記載する項目**

- 判定日時
- 技術制約の要約（要件定義書 1-1 の内容）
- 判断軸ごとの該当有無と理由（表形式）
- 候補の比較表（候補 / 判断軸ごとの評価 / 出典 URL / 確認日）
- 最終選定結果（言語、フレームワーク、DB、実行形態）と選定理由（業務要件との対応）
- ユーザー承認の記録（承認日）

**フロントエンドとバックエンドを分ける構成を選んだ場合の必須設計記載**

- フロントエンド：ビルド後の静的配信方式
- バックエンド：リバースプロキシの配置と API の経路（`/api/` を前提に統一する）
- 認証境界の位置

### 2. システム構成

- コンポーネント一覧（要件を根拠に表形式）
- システム全体構成図（mermaid）
- 各コンポーネントの役割と機能
- コンポーネント間インターフェースとデータフロー
- ネットワーク構成図（mermaid）

### 3. データベース設計

- DB の必須性を判定し、理由を必ず明記する
- DB が必須でない場合は「DB は必須ではないため、DB 設計は行わない」と明記する
- DB 製品は第 1 章の選定結果に従う。第 1 章で選定していない製品をここで持ち込まない

**DB 設計に含める項目**

- テーブル設計：カラム、型、制約を明記
- リレーション図：mermaid 形式で描画

### 4. アーキテクチャ設計

- 外部設計
  - UI設計（GUIなら画面一覧、画面遷移図、AAモックアップ。CUIならコマンド仕様）
    - 画面一覧：各画面の要素と機能を説明
    - CUI：コマンドや引数、設定の一覧を表にする
  - 外部システム連携（一覧、インターフェース、データフロー図）
    - 要件に外部連携がある場合、`external/[システム名]` を参照して設計を行うこと。
    - 外部連携先のシステムを呼び出す際には、`external/[システム名]/src` を使って呼び出す設計にすること。
    - 外部連携先のシステムを直接呼び出す設計は禁止する。
  - 外部DB連携（一覧、インターフェース、データフロー図）
- 内部設計
  - 処理フロー図（mermaid）
  - 各処理の役割と機能
  - 必要に応じたバッチ設計（フロー図、役割）

### 5. クラス設計

クラス設計にあたってはSOLID原則を遵守すること。

- 全クラス一覧と役割
  - SOLID原則への適合状況を表で明示
- クラスの責務、主要属性、主要メソッド
- クラス図（mermaid）
- システム内メッセージ一覧と役割
- メッセージフロー図（mermaid）

### 6. その他設計

- エラーハンドリング設計（想定エラー一覧）
- セキュリティ設計

### 7. コード設計

- ソースコードのディレクトリ構成（AA）：ファイル名を含めないこと
- 各ディレクトリ配下のファイル名、役割、含まれるクラスの一覧表：各行に関係する設計IDを明記すること
- 言語・フレームワークに応じたコーディング規約表
- コードには要件 ID・設計 ID を書かない。設計 ID とコードの対応は実装時に `docs/trace_map.md`（対応表）へ記録する旨を明記する（`.agents/skills/isdd-common/references/trace-map-rules.md`）

### 8. テスト設計

- テスト種別と内容
- 各テストの目的と方法
- 実装すべき全テストケース
  - 全モジュールの単体テスト
  - 全機能要件の結合テスト
  - システム全体の総合テスト
  - GUI/CUIがある場合のユーザー視点テスト（e2eテスト）

### 9. 運用設計

- 基本起動方式はdocker compose
- DBスキーマや初期ユーザー等の初期化が必要なら起動時自動化
- 起動方法と操作説明をREADME.mdに記載する旨を設計書に明記

### 10. ログ・監視・アラート設計

- ログ設計の必須性判定
  - 必須でない場合は「ログの設計は必須ではないため、ログの種類と内容の記述は行わない」と明記
- 監視・アラート設計の必須性判定
  - 必須でない場合は「監視・アラートの設計は必須ではないため、監視・アラートの内容と対応方法の記述は行わない」と明記
- 必須の場合は内容と対応方法を表で定義

### 11. E2Eテスト設計

**設計要件**

- 要件書のテスト用利用シナリオを 100% 網羅する
- 各シナリオごとに「目的、前提条件、手順、期待結果」を表で定義する
- GUI の場合は全画面遷移を網羅し、Playwright 前提で具体化する
- 外部連携がある場合、E2E は `mock` モードと `real` モードの2モードを設計する
- 設計上は全 E2E シナリオを `mock` / `real` の両モードで実行対象として定義する

**docker compose への test_playwright サービス追加**

- `mcr.microsoft.com/playwright:v1.59.0` を使用する
- プロファイル名は `test` に加えて、外部連携時は `mock` / `real` の切替プロファイルを定義する
- 通常起動では起動しない
- テストコードをマウントして即時反映できる構成にする

**E2E実行コマンドの設計**

設計に E2E 実行コマンドを明記する。実行コマンドは以下の形式を前提とする。

```
docker compose run --rm test_playwright sh -c "npm install && npx playwright test"
```

**E2E運用設計**

以下の項目を設計に含める。

- ファイル配置：プロジェクトルート `e2e` 配下にテスト資産を配置する
- 外部モックは `external/[システム名]/mock/` を正本とし、`e2e` 側はシンボリックリンクで参照する（Git 管理下に置く）
- モード切替は docker compose プロファイルとテスト実行コマンドの両方を提供する
- テスト環境作成スクリプトは原則 bash で実装し、複雑処理はメインプロジェクト言語または Python を利用する
- テスト実行時の URL は compose 内サービス名ベースで定義する
- 実装時・CI 時の必須ゴールは `mock` モード E2E 全件通過とする
- `real` モード E2E は手動実行のみ必須とする
- テスト失敗時は修正と再実行を繰り返し、全成功まで継続する方針を明記する
