# 不具合修正の扱い（isdd-spec）

変更フロー（正本の `docs/requirements.md` と `docs/detail_design.md` がある）で、依頼が不具合の報告（「バグを直して」「仕様どおりに動かない」「エラーが出る」「前は動いていた」など）のときに使う。

既存の要件が満たされていない不具合を、新しい要件として足さない。足すと、同じ動きを定めた要件が 2 つになり、元の要件が満たされていなかった事実も残らないため。直すのは設計かコードで、要件 ID はそのまま使う。

## 1. 切り分け

業務の問題・業務課題・見込み経営効果は聞き直さない（満たされていない要件に結びついた既存の `RQ-BK-*` を使う）。

1. 現象を確かめる。依頼に無いものだけを、番号を付けて 1 回の応答でまとめて聞く: 何をしたか（再現の手順）、何が起きたか、何が起きるはずだったか。
2. `docs/requirements.md` を読み、「起きるはずだった動き」を定めた要件を探す。機能（`RQ-FT`）・画面や出力（`RQ-UI`）・外部連携（`RQ-EX`）だけでなく、業務ルール、データ（`RQ-DT`）、非機能（`RQ-NF`）、運用（`RQ-OP`）、第 7 章のシナリオの「期待される結果」も見る。
3. 次の表で種類を決める。

   | 起きるはずだった動きを定めた要件 | 今の動き | 種類 | 進め方 |
   |---|---|---|---|
   | ある | その要件を満たしていない | 実装の不具合 | 下の 4 へ。要件は変えない |
   | ある | その要件どおりに動いている（それでは困る） | 要件の誤り | 通常の変更フロー（旧い要件を [削除]、新しい要件を [追加]）。spec-requirements.md の 1 から |
   | 無い | ― | 要件の欠け | 通常の変更フロー（要件を [追加]）。spec-requirements.md の 1 から |

   要件の文がどちらとも読めるときは、決めつけずにユーザーに読み方を聞く。
4. 実装の不具合なら、`docs/detail_design.md` とコードを読んで、原因のある場所を決める（コードは読むだけで、書き換えない。再現のために実行してよい）。

   | 原因のある場所 | 見分け方 | 直すもの |
   |---|---|---|
   | 設計 | 設計書の記述が要件を満たしていない（設計書どおりに作ると不具合になる） | 設計とコード |
   | コード | 設計書は要件を満たしているが、コードが設計書どおりでない | コードだけ |

5. 切り分けの結果を 1 回の応答で示し、ユーザーに確かめる。示すもの: 満たされていない要件の ID と本文の引用、種類、原因のある場所とその根拠（設計書の節、コードの場所）、「要件は変えずに直す」こと。要件が見つからなければ、「定めた要件が無いので、要件の追加として通常の変更フローで進める」と伝えて、そちらへ進む。ユーザーが「要件のほうを変えたい」と答えたら、通常の変更フローへ進む。

## 2. 書くもの

変更のディレクトリは `.history/[YYYYMMDD]-fix-[名前]/`（例: `.history/20250115-fix-total-rounding/`）。

| ファイル | 原因が設計 | 原因がコード |
|---|---|---|
| `bug_report.md`（不具合の記録） | 書く | 書く |
| `change_detail_design.md`（直す設計要素だけ） | 書く | 書かない |
| `change_requirements.md` | 書かない | 書かない |
| `tasks.md` | 書く | 書く |
| `docs/active_change`（変更のディレクトリを 1 行） | 書く | 書く |

正本（`docs/requirements.md`・`docs/detail_design.md`）は書き換えない。

### bug_report.md

見出し `# 不具合の記録` で始め、次の 2 つの表を書く（チェッカーは見出しでこの文書を見分ける）。

```markdown
# 不具合の記録

| 現象 | 再現の手順 | 期待する動き | 満たされていない既存の要件ID | 対応業務課題ID（RQ-BK-*） | 原因のある場所 | 原因 |
|---|---|---|---|---|---|---|
| 合計が 1 円ずれる | 税込 108 円の商品を 3 個入れて合計を見る | 324 円と表示する | `RQ-FT-CALC-ORDER-TOTAL` | `RQ-BK-REDUCE-BILLING-ERRORS` | コード | 設計書 5 章は合計してから端数を切り捨てるが、コードは 1 個ごとに切り捨てている |

## 再現するテスト

| 確かめる要件ID | 結ぶ DS-TS（既存） | テストの手順 | 期待される結果 |
|---|---|---|---|
| `RQ-FT-CALC-ORDER-TOTAL` | `DS-TS-ORDER-TOTAL-E2E` | 税込 108 円の商品を 3 個入れて合計を取る | 324 |
```

- 要件 ID と業務課題 ID は、正本にあるものをそのまま書く。新しい要件 ID を採番しない。[追加]・[削除] の行を書かない（要件やシナリオを足す必要があるなら、それは不具合修正ではなく通常の変更フロー）。
- 再現するテストは 1 本以上書く。直す前は落ち、直したら通るテストにする。受け入れ判定が合格していたのに不具合があったのは、今のテストが見逃していたためで、同じ不具合が戻ったときに気づけるようにする。
- 再現するテストは、その要件を「検証する要件ID」に持つ既存のシナリオ（`RQ-TS`）の `DS-TS` に結ぶ（`isdd-build` が対応表の `DS-TS` の行にテスト関数を足す）。シナリオの無い `RQ-NF`・`RQ-DT`・`RQ-OP` は、原因がコードでも変更設計書を書き、`DS-TS` を [追加] して第 11 章でその要件に直接対応させる。
- 調べている途中で別の不具合を見つけたら、表に行を足して同じように切り分ける。不具合を直すのに要らない機能や設計の変更は足さない。

### change_detail_design.md（原因が設計のとき）

spec-design.md の「変更フローで足すこと」と同じ書き方で、直す設計要素だけを書く。中身が変わる設計要素は旧い設計 ID を [削除]、新しい設計 ID を [追加] にし、第 11 章では既存の要件 ID に対応させる。技術選定、E2E の実行手段、連携ライブラリ、モック方式は、変えないかぎり承認を取り直さない。

### tasks.md

design-tasks-rules.md に従う。先頭の固定タスクのあとに「再現するテストを書き、直す前に落ちることを確かめる」タスクを置き、そのあとに直すタスクを並べる。

## 3. チェック

```bash
python3 .agents/skills/isdd-spec/scripts/rq_integrity_checker.py .history/[YYYYMMDD]-fix-[名前]/bug_report.md --base docs/requirements.md
# 原因が設計のときだけ（引用した要件が、直した設計要素に対応していることを確かめる）
python3 .agents/skills/isdd-spec/scripts/rq_ds_link_checker.py .history/[YYYYMMDD]-fix-[名前]/bug_report.md .history/[YYYYMMDD]-fix-[名前]/change_detail_design.md --base docs/requirements.md
```

`--base` を付けた整合チェックは、不具合の記録が引用する ID が正本に無ければエラーにする。エラーになったら、ID の写し間違いを直すか、要件の欠けとして通常の変更フローに切り替える。実行ログは応答に載せる。

## 4. 報告と承認

次を報告し、承認を求める。承認を得たら、`isdd-build` で実装と実装後レビューを行うよう案内する。

- `bug_report.md` の 2 つの表（文書から読み直して、表のまま貼る）
- 原因が設計のときは、[削除]・[追加] する設計 ID の一覧
- チェッカーの実行ログ
- 要件定義書を変えていないこと
