# 要件の除外と、設計から要件へのフィードバック

設計スキル（isdd-design、isdd-change-design）が使う。
下の「入力要件書」は、新規設計では `docs/requirements.md` の要件を、変更設計では `.history/[YYYYMMDD]-[タスク名]/change_requirements.md` の [追加] 要件を指す。

## 最小設計の意味

最小設計とは、入力要件書に無い設計要素を足さないことを指す。
入力要件書にある要件を設計から削るのは最小設計ではなく、要件違反になる。「最小構成のため」を理由に、ユーザーの承認なしで要件を外さない。

## 要件除外ゲート

入力要件書の要件 ID（`RQ-BK`・`RQ-BZ`・`RQ-EF` を除く）は、ユーザーが承認しない限りすべて設計に反映する。
設計の途中で外す必要があると判断したら、次の順に進める。

除外できるのは、他の要件の設計で実現済みの要件（変更設計では既存設計 `docs/detail_design.md` で実現済みのものも含む）だけにする。
実装できない要件や、他の要件と矛盾する要件は除外せず、下の「設計から要件へのフィードバック」で要件そのものを直す（削除・修正など）。要件を残したまま除外すると、要件定義書に実現されない要件が残るため。

1. 外したい要件 ID と、それを実現している吸収先の設計 ID を示す
2. ユーザーの承認を得る
3. 承認された場合だけ、設計書の「11-1. 除外要件」節に次の表で記録する。この節にある要件 ID には、チェッカーが設計 ID の対応を求めない

   | RQ-ID | 除外理由 | 吸収先 DS-ID | 承認日 |
   |---|---|---|---|
   | `RQ-NF-...` | `RQ-FT-...` の設計で実現済みのため | `DS-FN-...` | 2026-01-15 |

4. 変更設計では、正本へ反映するときに 11-1 の行も `docs/detail_design.md` の 11-1 に書き写す。書き写さないと、正本どうしでチェッカーを回したときに、除外した要件が未マッピングになるため

承認のない除外が残っているうちは、レビューへ進まない。

## 設計から要件へのフィードバック

設計中に要件 ID と設計 ID の未マッピングが出たら、次を繰り返して未マッピングをゼロにする。

1. 未マッピング一覧を要件単位で作る
2. 1 件ずつユーザーに聞き直し、「削除」「修正」「分割」「統合」「追加」のどれにするかを決める
3. 入力要件書そのものを直す。別の新しい変更要件に回さない（起点の要件書と設計書がずれたまま残るため）
4. 要件 ID を整理し直し、設計書の設計 ID（末尾の要件略称と、要件と設計の対応表）に伝える

設計スキルは、この手順を実装後レビュー（`isdd-post-implementation-review`）に任せず自分で行う。実装後レビューは実装が原因の差分だけを扱うため。
