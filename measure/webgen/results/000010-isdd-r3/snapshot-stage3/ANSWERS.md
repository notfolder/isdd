# ヒアリングへの固定回答（isdd 群、計測 4: WebGen-Bench）

ユーザーは不在。質問にはこのファイルの回答で答え、ここに無いことは依頼の文章（REQUEST.md）と契約（contract.md）から最も単純に決めて進める。承認（要件の確定、技術選定、E2E の実行手段、除外要件、設計の承認、実装と正本の確定）はすべて与えられたものとして進め、止まらない。

- 外部連携: 無い。既存ソースコード: 段 1 では無い（段 2・3 では段 1 までのコードと docs/ の正本がある。変更フローで進める）。
- システムの目的・業務課題・あるべき姿・現状: REQUEST.md の依頼文から読み取れる範囲で簡潔に書く。見込み効果は算定しない。
- 想定利用者: 一般の利用者（ログインは不要。利用者の区別が要る機能は依頼に書かれた範囲だけ）。
- 帳票・バッチ・API: 無い。ブラウザで使う画面だけ。
- データ: 依頼に出てくるものだけ。DATA_DIR の下に SQLite か JSON で保存。初期データ（サンプル）を起動時に入れる（契約）。
- 画面: 依頼の機能ごとに最小限。画面の言語は英語（契約）。
- 非機能: 利用者は少数、性能の目標は無い。認証無し。ログ・監視・バックアップは不要。
- 技術制約: Python 3.12 か Node.js 24。無償のものだけ。配備は `bash run.sh` で直接起動（契約）。
- 技術選定: 推奨の案でよい（Python のフレームワーク ＋ SQLite が最も単純）。
- E2E の実行手段: ローカルで直接実行。E2E は JUnit XML を `e2e/results/` に出す。ブラウザ自動化が使えなければ HTTP クライアントで実サーバーを確かめる形でよい。
- 対応表の粒度: function。依存の規則: 無ければ「無い」でよい。
- 要件の除外: 無し。依頼に無いことは作らない。
