仕入先「まるいち物産」の在庫照会 API（手元で立てる模擬の HTTP の API）から商品と在庫数を取り込み、自社の画面で一覧し、商品ごとに売価を入れるアプリ。段 1 で新しく作り、段 2 で「連携先の API が v2 に変わった」変更に対応する。

## 模擬の連携先に仕込んだ癖

| 癖 | 説明書の記述 | 実物の動き | 食い違い |
|---|---|---|---|
| ページ分割（v1） | `page`・`per_page`。`per_page` の上限は 100 | 上限は 50。それより大きい値は黙って 50 にする（応答の `per_page` は 50 と出る） | あり |
| 廃番（v1） | 廃番の商品は返さない | `discontinued: true` を付けて返す（説明書の応答例にこの項目は無い）。出すかどうかは依頼者が決める（E4） | あり |
| 回数の制限 | トークンごとに 1 秒 3 回（v2 は 2 回）。超えると `429` と `Retry-After` | 説明書どおり。`Retry-After` を待たずに来た要求を数える | なし |
| 認証の失効 | `expires_in` 秒、または一定回数の照会で失効。`401 token_expired` | 30 秒、または成功した照会 6 回で失効 | なし（回数は説明書に無い） |
| 障害 | `503` | 説明書どおり（採点器が止めたり、途中から止めたりする） | なし |
| ページ分割（v2、段 2） | カーソル方式。最後のページの `next_cursor` は `null` | 最後のページでは `next_cursor` のキーごと無い | あり |
| 在庫の内訳（v2、段 2） | `stock` が `{available, reserved}` | 通知どおり。どちらを出すかは依頼者が決める（E8） | なし |

回数の制限と失効は、発行したトークンごとに持つ。複数の実行が同じ共用サーバーを同時に使っても混ざらない。
抜け道: 照会のたびにトークンを取り直すと、回数の制限にかからない（トークンごとに数えるため）。この作りの実装は、回数の制限のテストを制限を守らずに通る。

## 起動

共用の連携先（作業中のエージェントが接続して調べる。v1 と v2 の両方を出す。180 件）。本番と試し回しの前に 1 つ起こしておく:

```bash
nohup python3 measure/extapi/mock/supplier_server.py --port 18080 --versions 1,2 --items 180 > /tmp/extapi-supplier.log 2>&1 &
```

採点用の連携先は `hidden/conftest.py` が空きポートに別に起こす。データはテストごとに入れ替える（商品コードは `ZK-`、共用は `MB-`）。アプリには `SUPPLIER_API_URL`・`SUPPLIER_CLIENT_ID`・`SUPPLIER_CLIENT_SECRET` で渡す。

実行（依頼者役あり。契約は段ごとの既定を使うので `--contract` は付けない）:

```bash
python3 measure/run.py --arm control --run 1 --model claude-opus-5-5 --work /Users/Shared/isdd-measure-work --task extapi --stages 1,2 --max-rounds 20 \
  --responder measure/extapi/ledger.md --path-prefix /tmp/isdd-measure/bin              # バイブコーディング
python3 measure/run.py --arm control --ask-first --label extapi-ask-opus-r1 …           # 一文つき
python3 measure/run.py --arm isdd …                                                     # isdd
```

採点だけ: `measure/.venv/bin/python measure/extapi/score.py --app <アプリ> --stage 1 --out <JSON>`

## 台帳の事実と、質問・要件・実装・テストの対応

「質問で出る」は、依頼者役がその事実を話すきっかけ。「要件に入る」「実装される」は、その事実が成果物でどう現れるか。追うときは、会話の記録（`stage<N>.log`）→ 要件の文書か決め事のメモ → コード → 下のテスト、の順に見る。

| 番号 | 台帳の事実 | 質問で出る | 要件に入る | 実装される | 確かめるテスト |
|---|---|---|---|---|---|
| E1 | 取り込みは「最新にする」の操作のときだけ。見るだけでは連携先を呼ばない。定期の取り込みは要らない | 「取り込みはいつ行うか」 | 取り込みのきっかけ。定期実行は作らない | 一覧は保存した内容から出す。定期実行のコードが無い | `test_ext_view_does_not_call_supplier` |
| E2 | 連携先が止まっているときは、前回の内容を見せ続け、失敗と最後に成功した日時が分かる。復旧後は元どおり | 「連携先が止まっているときどう見せるか」。広い質問でも出る | 障害時の表示 | 取り込みの失敗でデータを消さない。結果と成功日時を保存する | `test_ext_outage_keeps_previous_items`、`test_ext_outage_status_failed_and_last_success_kept`、`test_ext_recovers_after_outage`、`test_ext_first_sync_failure_shows_empty` |
| E3 | 途中で失敗した取り込みは混ぜない。全部取れたときだけ入れ替える | 「取り込みが途中で失敗したらどうするか」 | 取り込みの単位（全部か無しか） | 全件を集めてから 1 回で入れ替える | `test_ext_partial_failure_keeps_previous_whole` |
