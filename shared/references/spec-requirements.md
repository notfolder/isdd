# 要件の段階（isdd-spec）

業務課題に結びついた最小の要件を、インタビューで確定して文書にする手順。新規開発と変更開発で、書く先と書き方だけが違う。

| フロー | 書く先 | 書き方 |
|---|---|---|
| 新規 | `docs/requirements.md` | 章立て（requirements-chapters.md）どおりに全章を書く |
| 変更 | `.history/[YYYYMMDD]-[タスク名]/change_requirements.md`（タスク名は `20250115-add-user-profile` の形） | 変更する要件だけを [追加] [削除] で書く。正本の `docs/requirements.md` は書き換えない |

変更フローで正本を書き換えないのは、正本に実装していない変更を重ねないため（新規フローの正本は isdd-spec が実装前に書くが、変更フローの差分は実装後に `isdd-build` の実装後レビューが合流させる）。実装前に書き換えると、作らなかった変更が正本に残るため。

## 1. 業務の問題と業務課題

要件の最初に、業務の問題と業務課題を確定する。isdd ではすべての要件を業務課題に結びつけるので、業務課題が決まる前に機能・画面・外部連携・非機能の質問を始めない。
問題は業務のあるべき姿と現状のギャップ、課題（業務課題）は問題を解決するために取り組むアクションやテーマを指す（requirements-chapters.md の「用語: 問題と課題」）。
この段階の問いは前の答えで次の問いが変わるので、1 問ずつ順に聞く。

1. 作りたいもの（変更なら今回の変更）をユーザーが既に話していればそれを使う。話していなければ「一言で言うとどのようなアプリですか？」（変更なら「一言で言うと今回どのような変更ですか？」）と聞く。
2. 変更フローでは、先に `docs/requirements.md` を読んで既存の要件を理解する。
3. 対象業務を `RQ-BZ-*` で採番し（変更フローで既存の業務なら既存の ID を使う）、業務ごとにあるべき姿と現状を聞いて、そのギャップを業務の問題として確定する。できるだけ KPI の数値で聞く。
4. 問題ごとに、解決のために取り組むことの候補をいくつか示し、ユーザーが取り組む業務課題を特定する。
5. 業務課題を `RQ-BK-*` で採番して確定する。
6. 業務課題を解決したときの見込み経営効果を聞き、`RQ-EF-*` で採番する（変更フローでは、効果に変わりがあるかを聞く）。算定できなければ、その理由を書く。

## 2. ヒアリング

質問は hearing-rules.md に従う。要点:

- 依存のある問いは 1 問ずつ、独立した問いは番号を付けてまとめて出す。業務課題が決まった後の各章（機能、画面・出力、業務ルール、データ、非機能、運用、テスト用利用シナリオ）は、章の中の独立した問いをまとめて出せる。
- 選択肢を伴う問いには、最初に出すときから次の表を付け、表の下に「推奨: 〇〇（理由を一文）」と書く。推奨は、業務課題を満たす中で複雑さが最小の案にする。表が無いと、ユーザーは選択肢の重さを比べられないため。

  | 案 | 内容 | メリット | デメリット | 複雑さ（C=1〜5） | 根拠（効いている評価軸） |
  |---|---|---|---|---|---|

- ユーザーが推奨より複雑な案を選んだら、次の順に進める（hearing-rules.md の「推奨より複雑な案が選ばれたとき」）。
  1. 次の応答では他の問いと混ぜずに、「最小案では満たせない業務上の理由は何か」を尋ね、最小案と選ばれた案の違い（複雑さと、それぞれで業務に起きること）を示す。
  2. 理由が具体的でなければ、選び直しを 1 度だけ求める。それでも同じ案なら、ユーザーの選択に従う。
  3. その要件の「この要件が無いと何が困るか」列に、「ユーザーの選択（理由: ユーザーが述べた言葉をそのまま）」と書く。理由が無ければ「ユーザーの選択（理由は特に無い）」と書く。エージェントが理由を作って書かない（後で経緯を確かめるとき、本当の理由と区別できなくなるため）。
- システムの形態ごとの確認項目（hearing-rules.md）を聞き、該当する節に書く。CUI ならコマンドごとに、引数、出力、終了コード、エラー時の表示を書く。
- 技術制約（既存コードベースの言語、配備先、チームが扱える技術と禁止技術、ライセンスとコスト、性能と規模の目安）を確認し、「1-1. 技術制約」に書く。「特に無い」も回答として書く。変更フローで変更が無ければ「変更なし。既存要件定義書 `docs/requirements.md` 1-1 を参照」と書く。言語や製品名をこちらから勧めない（選定は設計の段階で候補を比較して行うため）。
- 分からない点が残る限り質問を続ける。推測で埋めた箇所を残さない（設計はこの文書だけを根拠にするため）。
- 依頼や回答に無いことを決めるときは hearing-rules.md の「依頼文に無い決め事」に従い、「1-2. 依頼に無く自分で決めた項目」の表に書く。 要件の問いを出す前に、hearing-rules.md の洗い出しの表（入力ごとの無い・空・形式違い、出力ごとの 0 件、操作ごとの同時・繰り返し）を対象ごとに当てはめ、依頼に無いものを問いに入れる。

## 3. 要件の書き方

### 共通

- ID は id-definitions.md に従って付ける。業務は `RQ-BZ-*`、業務課題は `RQ-BK-*`、見込み経営効果は `RQ-EF-*`、機能と業務ルールは `RQ-FT-*`、画面・帳票・Web API は `RQ-UI-*`、外部連携は `RQ-EX-*`、データ章の各要件は `RQ-DT-*`、非機能要件は `RQ-NF-*`、運用要件は `RQ-OP-*`、テスト用利用シナリオは `RQ-TS-*`。
- `RQ-BK` と `RQ-BZ` 以外の要件には、対応する `RQ-BK-*` を 1 つ以上、同じ表の「対応業務課題ID」の列に書く。結びつかない要件は、削除するか業務課題を追加してから定義し直す。
- `RQ-FT`・`RQ-UI`・`RQ-EX` は、第 7 章のシナリオの「検証する要件ID」に 1 本以上現れるようにする（受け入れテストの無い要件を残さない。`RQ-NF` は確かめたいものだけ書く）。
- 業務課題と要件の対応表（`RQ-BK-*` と `RQ-*` の対応）を作る。
- 各要件に「この要件が無いと何が困るか」を書く。説明できない要件は削る。
- 同じ目的の要件は 1 つにまとめる。
- 将来の拡張、一般論、ベストプラクティスは書かない。今回の業務課題に要るものだけにする。
- 文書の書き方は document-rules.md に従う。

### 変更フローで足すこと

- すべての要件項目に [追加] か [削除] を書く。「変更」という区分は使わず、変える要件は旧要件を [削除]、新要件を [追加] に分けて書く。区分が 2 つだけなら、正本へ反映するときに機械的に処理できるため。
- 要件の意味が変わる場合は、旧要件を [削除]（`deprecated`）とし、新しい `RQ-*` ID を採番して [追加] する。
- [削除] 要件には削除理由と、不要になる、または解消される `RQ-BK-*` を書く。
- CRUD テーブルは、変更の有無にかかわらず全エンティティ分を書く（変更の影響が他のエンティティに及んでいないかを確かめるため）。
- 変更が無い章は「変更なし。既存要件定義書 `docs/requirements.md` セクション[N] を参照」とだけ書く。
- [追加] の `RQ-FT`・`RQ-UI`・`RQ-EX` を確かめる `RQ-TS` の行を第 7 章に書く。既存のシナリオの「検証する要件ID」だけを変えるときは、同じ `RQ-TS` を [削除]（旧い列）と [追加]（新しい列）の 2 行で書く。第 7 章を「変更なし」にできるのは、[追加] の `RQ-FT`・`RQ-UI`・`RQ-EX` が無いときだけ。
- 変更後の業務課題と要件の対応表を書く。
- 既存要件と同じ目的の要件は足さない。

## 4. 網羅性チェック

要件を書いたら次を確認し、不足があれば直す。変更フローでは、追加・削除する要件と、その影響が及ぶ範囲について確認する。

- 業務の問題（あるべき姿と現状のギャップ）を書き、すべての業務課題に解決する問題があるか
- 業務エンティティをすべて列挙し、エンティティごと（変更フローでは追加・変更するもの）にデータ項目（必須、形式・桁、値の範囲）を書いたか
- 各エンティティの CRUD テーブル（4-3）を全エンティティ分書いたか
- マスタに当たるエンティティに管理機能があるか
- 機能カテゴリ（業務機能 / マスタ管理 / 共通（認証・認可・ログ）/ 運用 / 外部連携）を検討したか
- 状態を持つエンティティの状態遷移（4-4）を定義したか（変更フローでは影響が無いかを確かめ、変わる遷移を書いたか）
- 業務ルール（3-2）、帳票・出力ファイル（3-1）、外部連携（3-3）、非機能要件の可用性と移行性、運用要件（第 6 章）を、無い場合も「無い」と書いたか（変更フローでは影響を確かめたか）
- 機能と画面・ユーザーフローの対応を確かめたか
- 削除できる要件を列挙し、削除しても業務が成り立つ要件を実際に削除したか
- ユーザーが推奨より複雑な案を選んだ要件の「この要件が無いと何が困るか」列が、「ユーザーの選択（理由: ユーザーが述べた言葉）」または「ユーザーの選択（理由は特に無い）」になっているか
- すべての要件項目に `RQ-*` ID があるか（変更フローでは [追加] か [削除] の区分もあるか）
- すべての `RQ-BK-*` に対応する要件が 1 件以上あり、`RQ-BK`・`RQ-BZ` 以外のすべての要件に対応する `RQ-BK-*` があるか（変更フローでは [削除] 要件に不要になる `RQ-BK-*` が書いてあるか）
- すべての `RQ-FT`・`RQ-UI`・`RQ-EX` が、第 7 章のいずれかのシナリオの「検証する要件ID」に現れるか（変更フローでは [追加] の要件について）
- 外部連携がある場合、外部連携の段階（spec-external.md）の整合確認の結果を反映したか

## 5. 整合チェック

要件の文書ができたら、次を bash で実行する（変更フローでは変更要件定義書を渡す）。

```bash
python3 .agents/skills/isdd-spec/scripts/rq_integrity_checker.py docs/requirements.md
python3 .agents/skills/isdd-spec/scripts/rq_integrity_checker.py .history/[YYYYMMDD]-[タスク名]/change_requirements.md
```

チェッカーは、カテゴリの書式違反、`RQ-BK` との対応が無い要件、対応する要件が無い `RQ-BK`、どのシナリオの「検証する要件ID」にも現れない `RQ-FT`・`RQ-UI`・`RQ-EX` を報告する。問題があれば直して再実行し、0 件になってからレビューへ進む。実行ログは応答に載せる。

## 6. レビュー

document-rules.md のレビュー項目に加えて、次を確認する。問題があれば直してから報告する。

1. 網羅性チェックをすべて満たしているか
2. 業務課題と要件の対応が両方向に成り立っているか
3. 変更フローの場合、`docs/requirements.md` を書き換えていないか
4. 依頼や回答に無いことを決めていれば、すべて「1-2. 依頼に無く自分で決めた項目」の表にあるか（本文に書いただけで表に無い決め事を残さない）。無ければ「無し」と書いてあるか
